# serve 轮询：`smctl run serve --watch` 等复审裁决、跑到请求结束

状态：用户已决定（2026-10-16，第 5 节四项均选推荐项）；合同一 `ledger-catch-up` 完成，合同二 `serve-watch` 进行中。

## 1. 为什么做

`serve`（serve-loop）和 `serve --parallel`（serve-parallel）都只走一遍：
- 任务进了复审（`REVIEW_PENDING`）就跳过；
- 操作员下了裁决之后，要再手动敲一次 serve，才会领被拒绝任务的下一次尝试。

一个八个任务的请求，要操作员在“看复审 → 下裁决 → 再 serve”之间来回好几趟。两份设计说明都把“守护进程、轮询等待复审”列在“不做”里，留给以后。

2026-10-16，用户在 Code-Kit 2.10.0 之后选了“3 → 2 → 1”，这是其中的第 2 项。

## 2. 现状（2026-10-16 核对）

**账本是单写者**
- `DurableScheduler` 的文档串写明：一个实例是它那份日志的唯一写者。
- 每次变更先在内存里执行，再在一个 `BEGIN IMMEDIATE` 事务里追加。追加前核对日志头：日志头不是自己上次写的，就是 `E_LEDGER_STALE`，实例整个失效，之后读写都拒绝。
- 读视图（`task`、`status`）只看实例打开时重放出来的内存状态，看不到别的进程后来写的东西。

**实测后果（2026-10-16，真实 `smctl` 进程，本机）**

步骤：
1. `serve --parallel 1` 有一个运行在跑；
2. 这时操作员从另一个进程敲 `smctl ledger stop`，它成功了；
3. 运行结束时，serve 去写账本，得到 `E_LEDGER_STALE`。

结果：
- serve 退出 3，报告里 `runs` 为空，拒绝点名了那个操作；
- 账本里那个操作停在未决状态，预算的保留量（40 token、20 cost）还挂着；
- 要 `smctl run recover` 才能接手，而 `recover` 会换代，并让请求停在 `RECOVERY_REQUIRED`。

这一条对今天的 `serve`、`serve --parallel` 和 `once` 都成立：任何一次长时间运行期间，操作员都不能写同一份账本。轮询模式要整夜挂着等操作员下裁决，正好撞在这上面。

**其它事实**
- `smctl ledger verdict`、`stop`、`resume`、`settle`、`resolve` 都是各自打开账本、写一条、关掉。
- `smctl run recover` 用换代（generation）把旧控制器隔离出去，旧控制器之后的写入得到 `E_FENCED`。
- `compact` 在一个事务里写检查点并删除它覆盖的命令。实例的 `(seq, sha)` 落在检查点之前时，无法从日志补上中间的命令。

## 3. 方案草图

分两份合同，先账本、后命令。

### 3.1 账本补读（合同一：`ledger-catch-up`）

**写入前补读**
- 每次变更时，在拿到写锁（`BEGIN IMMEDIATE`）之后、执行内存调用之前，先把日志里在本实例 `seq` 之后的命令按顺序重放进内存。规则和打开账本时的重放一样，链式摘要逐条核对。
- 然后才执行这次变更、追加、提交。
- 写锁从补读一直持有到提交：两个进程的写入由 SQLite 串行化，每个写入都基于最新的状态做判断。
- 被换代隔离的旧控制器补读之后，自己的写入照样得到 `E_FENCED`。这正是换代想要的效果。

**读之前补读**
- 新增 `refresh()`：在一个读事务里补读。
- 读视图不自动补读（行为不变）。serve 在每次领取之前调用 `refresh()`。

**补不上就是 `E_LEDGER_STALE`，补读的内容坏了另有错误码**
- 日志里本实例之后的第一条命令接不上本实例的头（另一段历史），或者检查点越过了本实例（它需要的命令已被删掉），都是 `E_LEDGER_STALE`，实例失效。后一种必然也表现为前一种，所以不单独规定检查点检查。
- 要补的命令里有 `rollover`：`E_LEDGER_STALE`，一条也不补。换代就是另一个控制器接管（`smctl run recover`），旧实例不能补读到新的代继续写，否则一个其实还活着的旧控制器会绕过换代隔离。
- 新命令之间链断了：`E_LEDGER_CHAIN`；调度器重放时拒绝（包括复用已有操作 id 的领取）：`E_LEDGER_REPLAY`。实例都失效。

**`compact` 不变**
- 日志头不是自己的仍然 `E_LEDGER_STALE`。要压缩就先 `refresh()`。

**失效规则不变**
- 补读当中的任何异常（含中断）都让实例失效：内存可能已经变了一半。

**效果**
- 操作员在 serve 运行期间敲 `smctl ledger verdict` / `stop` / `resume`，serve 的下一次写入或下一次 `refresh()` 就会看到。
- 上面实测的那种失败就没有了，所有命令都受益。

### 3.2 轮询（合同二：`serve-watch`）

新参数 `--watch`（可与 `--parallel N` 同用；不加 `--watch` 时 serve 与今天完全一样）。

**轮询的节奏**
- 一遍走完、在跑的运行都结束之后，不退出：等 `--poll-seconds`（缺省 30），`refresh()`，再走一遍。

**下一遍领什么**
- 只有被复审**拒绝**（`REJECTED`）的任务，才在下一遍领下一次尝试。
- 上一次运行没有进入复审就结束的任务（`NOT_STARTED`、`START_UNKNOWN` 等），轮询不替操作员重试，记为 `needs_operator` 跳过。否则，环境坏了的任务每 30 秒就会烧掉一次尝试次数（serve-loop 第 6 节的同一条教训）。

**什么时候结束**（报告的 `stopped`）
- `finished`：请求里每个任务都已接受、次数用尽，或者在等操作员处理；同时没有运行在跑、没有任务在等复审。
- `--max-seconds` 到了；
- Ctrl-C：与 `--parallel` 相同，第一次收尾，第二次放弃；
- 拒绝：账本不该再动的那类，与今天相同。

**报告**
- 最后写一行，在今天的键上加：
  - `"passes": N`（走了几遍）；
  - `"watch": {"poll_seconds": …}`。
- `runs` 按领取顺序，包含所有遍。

**逻辑时钟**
- 每遍继续递增，不回绕。

**原生证据**（Windows，真实进程）
1. serve `--watch` 跑两个任务，都进入复审；
2. 另一个进程接受一个、拒绝一个；
3. 下一遍领被拒绝任务的第 2 次尝试；
4. 再接受它之后，报告 `finished`，`passes` 为 3。

另有一条用例：运行在跑时，从另一个进程 `stop`，serve 补读后收尾，并停在 `E_STOPPED`，而不是 `E_LEDGER_STALE`。

## 4. 证据边界

- 全部离线：`offline` adapter、`python -c` 作业。真实 pi 不跑。
- 补读只在本机 SQLite 上证明：网络文件系统、多台主机共用一份账本仍然 NOT_RUN，与今天相同。
- 决策模型（Jev）在本轮是 shadow：变异等价（D2）的答案只记录，用来和规划端标的“等价 / 预期漏掉”对照。

## 5. 用户决定（2026-10-16，均选推荐项）

1. **裁决怎么进到长时间运行的 serve**：账本补读（第 3.1 节）。`smctl ledger …` 照常用，所有命令都受益。
2. **下一遍重领哪些任务**：只重领被复审拒绝的；没进复审就结束的跳过，记 `needs_operator`。
3. **什么时候结束**：请求里没有能再推进的任务时结束（`finished`），另有 `--max-seconds` 与 Ctrl-C。
4. **范围**：一次 `--watch` 只管一个请求。

## 6. 规划端决定

- 前台进程，不做系统服务、不脱离终端。要长期跑，就交给终端、任务计划程序或 `nohup`。
- 合同一先做：补读改的是账本的核心不变量（“唯一写者”变成“串行化的多写者”），要单独验收。合同二建立在它之上。
- 写入的顺序：先 `BEGIN IMMEDIATE`，再补读，再执行内存调用，然后追加、提交。写锁一直持有到提交，两个进程的写入就由 SQLite 串行化。实测：两个进程从同一条起跑线各写 120 条，用延迟事务时会丢写入，用 `BEGIN IMMEDIATE` 时一条不丢。
- 调度器自己的拒绝（`ContractError`）仍然不让实例失效：回滚事务，补读到的状态保留，因为那些命令已经在日志里了。内存调用的其它异常原样抛出，并让实例失效，与今天相同。
- `create_ledger` 的内存调度器改用 `_ReplayScheduler`：补读别的实例的领取时，要沿用日志里记下的操作 id。
- 补读时用的“已用操作 id”表，从内存里现有的操作现场构造。这样本实例自己的领取也在表里，不必另外维护一份。
- `refresh()` 在读事务里补读，不写任何东西，返回 `{"seq", "applied"}`。读视图不自动补读：每次读都开事务会改变所有读命令的代价，需要最新状态的调用方（serve）自己调用 `refresh()`。
- 留给合同二：换代之后 `ledger.generation` 读到的是新代。serve 现在每次领取都读一次 `ledger.generation`，旧控制器若在 `recover` 之后还活着，又补读到了新代，就可能用新代继续领取（今天只靠 `recover` 让请求停在 `RECOVERY_REQUIRED` 来挡）。合同一已经规定：补读遇到 `rollover` 就让实例失效，所以旧控制器的下一次写入会是 `E_LEDGER_STALE`。合同二仍在命令开始时把代读一次，之后一直用它。

## 8. 不做

- 系统服务、开机自启、远程控制。
- 跨请求轮询（若第 5 节第 4 项选“一个请求”）。
- 自动重试没进复审的运行（若第 5 节第 2 项选推荐项）。
- 网络文件系统上的多写者。
