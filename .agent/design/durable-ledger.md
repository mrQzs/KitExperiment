# 设计说明：持久调度账本（macOS 单宿主）

状态：用户同意方向（2026-10-08：“可以”），第 5 节的语义已确认（均选推荐项），按第 7 节拆分合同
前置：调度器接线（`.agent/design/scheduler-supervisor-wiring.md`）与输出流信任边界（`.agent/design/stream-trust-boundary.md`）都已集成

## 1. 为什么做

- IMPLEMENTATION_STATUS 把“持久调度账本”列为 NOT_RUN。
- 现在控制器进程一退出，账本就全部丢失：领取、预留、资源占用、用量、停止标记与代际都在内存里。换代恢复（`rollover()` 加 `recover_supervised_operation`）只能在同一个进程里演示，真正的“控制器崩溃后重启”还做不到。
- 07 设计文档第 4.3.3 节建议用本地 SQLite 作单宿主的权威领取与预算账本，短写事务用 `BEGIN IMMEDIATE`；第 8.2 节的崩溃窗口表要求重启之后按权威事实恢复，不能凭进程内的记忆。

## 2. 现状

- `sentinelmesh/scheduler.py`：内存 `Scheduler`，07 附录原型的后继。
  - 16 个变更方法，由一把 `RLock` 串行；
  - 被拒绝的调用不改变账本，scheduler-exact-inputs 的 oracle 对每个方法穷举守护；
  - 唯一的非确定性来源是 `claim` 里用 `uuid4` 生成的操作 id；时间都由调用方显式传入（`now`）。
- `sentinelmesh/persistence.py`：`DurableStore`（SQLite WAL、`synchronous=FULL`，资源、幂等记录、代际围栏、哈希链日志），没有接到 Scheduler。
- 07 附录 B.4 的 `ledger_ref.py`：用 SQLite 表实现的参考账本（DELETE journal、`synchronous=FULL`），是现有 Scheduler 的前身。之后 Scheduler 新增的语义都不在它里面，包括精确类型、监督相关的迁移、恢复、只读视图与用量映射。
- SQLite：venv 的 Python 3.12 链接 3.53.1，含 WAL-reset 的修复；系统 Python 3.9 是 3.43.2，不含。项目要求 Python ≥ 3.10。
- 18 个测试文件直接读 Scheduler 的私有属性（`_operations`、`_requests` 等）。

## 3. 两种做法

### 3.1 命令日志加重放（推荐）

- 内存 Scheduler 仍是唯一的语义实现，外面套一层持久账本：
  - 每个变更方法在内存里执行成功之后，把“方法名、参数，以及 `claim` 生成的操作 id”作为一条命令，追加到 SQLite 命令日志（带哈希链），追加成功才算提交；
  - 打开账本时按序重放全部命令，重建出与崩溃前完全相同的状态，连 `events` 的序号都相同；
  - 追加时核对日志的最新序号等于本实例已经应用到的序号。不等就说明别的进程（例如换代之后的新控制器）已经写过，本实例是过期的。
- 优点：
  - 不重写已有语义，已有的穷举测试继续守护它；
  - 改动集中在一个新模块。
- 缺点：
  - 运维核对要靠重放之后的只读视图，不能直接对表跑 07 第 8.4 节那样的 SQL；
  - 同一时刻只有一个实例能写。这正是“单宿主、单个活动控制器”的设定。

### 3.2 关系表（07 附录的做法）

- 把账本搬进 SQLite 表，每个方法一个 `BEGIN IMMEDIATE` 事务，检查与写入都在事务里。
- 优点：可以直接用 SQL 查询；多个进程可以交替写同一个账本。
- 缺点：
  - 要把约 900 行语义重写成 SQL 读写，形成两套实现，容易漂移；
  - 已有测试大量读私有属性，不能直接复用；
  - 工作量大约是 3.1 的三到四倍。

## 4. 命令日志的细节

- 日志是一个独立的 SQLite 文件：
  - DELETE journal、`synchronous=FULL`、`fullfsync=ON`（macOS 上普通 fsync 不刷磁盘缓存）；
  - 表 `meta`（格式名与版本）与 `commands`（`seq`、命令的规范 JSON、SHA-256、前一条的 SHA-256）。
- 一条命令是 `{"method", "arguments", "operation_id"}`，`operation_id` 只在 `claim` 时出现。被拒绝的调用不记；每个成功的变更调用都记，包括按幂等键重放的 `claim`（见 L5；durable-ledger a001 复审时更正）。
- 原子性：
  - 先在内存里执行。被拒绝的调用不改账本，所以直接把异常交给调用方。
  - 执行成功之后，在一个 `BEGIN IMMEDIATE` 事务里核对序号并追加。
  - 追加失败（磁盘错误、锁超时、序号不符）时，内存已经变了而日志没有：按第 5 节第 2 条失败关闭。
- 打开时：
  - 校验格式版本与哈希链，然后逐条重放；
  - 任何一条重放报错、哈希链断开、版本不符，都拒绝打开，不猜。
- 代际：`rollover()` 也是一条命令。新控制器打开账本、重放、`rollover()`；之后旧控制器的任何变更，都会因为序号不符而被拒绝。
- 读：`snapshot`、`operation`、`events`、`generation` 都读内存，不碰日志。

## 5. 用户决定（2026-10-08，均选推荐项）

1. **持久化方式**：命令日志加重放（第 3.1 节）。内存 Scheduler 仍是唯一的语义实现。
2. **追加失败，或日志已被别的进程推进**：失败关闭。本次调用报错，这个账本实例此后拒绝一切调用（包括读），必须重新打开（重放）才能继续。
3. **重启之后的在途操作**：交接时把运行描述（规格的各个字段、证据目录、worktree）记进账本；重启之后，由恢复驱动对换代前的在途操作逐个调用 `recover_supervised_operation`。

## 6. 规划端的决定（2026-10-08）

- L1：日志用 DELETE journal、`synchronous=FULL` 与 `fullfsync=ON`，与 07 附录的保守选择一致。WAL 的安全性依赖 SQLite 版本，单写者也用不着它。断电之后的持久性没有实测，仍记 NOT_RUN。
- L2：日志带格式名与版本；不符时拒绝打开，不自动迁移。
- L3：不做快照与压缩。重放的代价与命令数成正比，以后需要时再做。
- L4：不改内存 Scheduler 的语义与私有属性，已有测试原样保留。唯一的改动是把生成操作 id 的那一行提成一个方法 `_new_operation_id()`，好让重放时注入原来的 id。
- L5：先执行、后记录。
  - 内存 Scheduler 先执行调用：它被拒绝时账本不变，异常原样交给调用方，日志不记。
  - 执行成功之后，把绑定到参数名的全部参数（`Mapping` 转成 dict，列表照旧）连同 `claim` 生成的操作 id 编码成一条命令，在 `BEGIN IMMEDIATE` 事务里核对日志头之后追加；追加成功才返回。
  - 命令用保留键序的 JSON 编码（不排序键：`settle` 按映射自己的顺序记录用量，重放必须看到同样的顺序），不经过 2**53 的规范整数限制，所以 `now` 这类不进事件的大整数也能记录，不会因此让实例失效。原稿写的是“排序键”，与合同矛盾，durable-ledger a001 的执行器按合同实现并指出了这一点。
  - 所有成功的变更调用都记，包括按幂等键重放的 `claim`、`observe` 返回 REPLAY 的调用：重放它们同样不改变状态，或者产生同样的事件。
- L6：追加报错时，返回给调用方的错误表示“结果未知，重新打开之后再看”：提交本身可能已经落盘（07 第 4.3.5 节的提交不明）。凭幂等键与只读视图核对，不要直接重做。
- L7：打开与创建分开：`create_ledger(path)` 遇到已存在的文件就拒绝，`open_ledger(path)` 遇到不存在的文件就拒绝，避免路径写错时悄悄新建一个空账本。

以上决定都可以在后续合同里修改；改动时更新本节。

## 7. 合同拆分

1. `durable-ledger`：
   - 新模块 `sentinelmesh/durable_ledger.py`：命令日志、`create_ledger` / `open_ledger`、持久账本（同样的 16 个变更方法与只读视图）、过期检测、失效状态；
   - `scheduler.py` 只提出 `_new_operation_id()`。
   - 用真实的多个进程测试：进程被 `kill -9` 之后重新打开；另一个进程 `rollover()` 之后，旧实例的变更被拒绝；篡改、断链、格式不符与写入失败都失败关闭。
2. `restart-recovery`：
   - 交接时记录运行描述（`Scheduler.handoff` 新增可选参数，持久账本随命令一起记下）；
   - 恢复驱动：打开账本、换代，再对换代前的在途操作逐个调用 `recover_supervised_operation`；
   - 用真实进程演示“控制器在运行中途被杀、重启之后恢复”的完整流程。

## 8. 不做

- 不做多宿主、分布式锁与网络文件系统上的账本。
- 不承诺断电之后的持久性；Linux 与 Windows 仍是 NOT_RUN。
- 不调用真实 provider CLI，不读取凭据，不联网。
