## 1. 目标与非目标

### 1.1 原文目标与首期范围

使调度器能够识别、校验、组合并锁定**仓库内、明确启用、经受信管理流程登记的声明式任务插件**。派遣前识别版本、平台、角色能力、资源路径、权限与检查覆盖问题；把实际采用的完整内容作为审核输入。[^P06]

首期不扫描用户目录、不访问网络市场、不自动下载依赖，也不把“仓库里存在某目录”当成启用或信任。任务插件、runtime adapter 与 host adapter 使用不同注册及加载机制。任务插件是数据，不是向调度器注入 Python/JavaScript 回调的途径。

不替换 G0–G6、独立验收、候选快照、保护路径和用户授权。插件返回报告、生成检查模板或者引用 shell 脚本，都不会自动取得运行、安装、提交或写证据权限。Pi 自动发现扩展、技能、模板的禁用约束继续保留；06 不负责把任务插件安装为 Pi 原生扩展。[^P04][^P06]

### 1.2 审阅结论与优先补强项

原文方向清楚，关键不足在“校验什么、锁定哪些字节、由谁消费、发生竞态时如何拒绝”尚未形成完整契约。

| 原文尚未展开的环节 | 可能的错误 | 本版落点 |
|---|---|---|
| manifest 仅有字段组 | 各实现对默认值、未知字段和空值理解不一致 | 4.1.2–4.1.4、附录 A |
| 依赖无环但缺确定性规则 | 精确版本冲突被加载顺序掩盖 | 4.1.5–4.1.7 |
| 资源“实际使用”不够可判定 | `$ref`、模板 include、脚本导入绕开锁 | 4.1.8–4.1.10、4.2.1 |
| 只给出路径归属原则 | 链接、硬链接、大小写别名或检查后替换穿透边界 | 4.2.2–4.2.4 |
| 当前锁与历史锁关系不明 | 更新 `.agent/plugins.lock.json` 后旧引用悬空 | 4.2.6–4.2.9 |
| 发布缺并发/崩溃规则 | 最后写入者覆盖，半成品或孤儿文件被当成当前有效锁 | 4.2.7–4.2.10、8 |
| 只描述权限交集 | 作用域不同的同名权限被错误合并 | 4.3.1–4.3.3 |

| 验收缺可执行夹具 | 单元通过被误报为生产审核接线通过 | 7、附录 B/C |

### 1.3 必须保持的不变量

| 编号 | 不变量 |
|---|---|
| I01 | 显式启用、来源信任、内容完整、审核有效、业务授权、实际执行、候选通过是不同事实。 |
| I02 | 只接受声明式 `task`；manifest 中没有 `entrypoint`、`loader`、`hook`、动态 import 或安装脚本入口。 |
| I03 | 每个已解析插件 ID 只有一个精确版本；不联网求解，不“选最新”，不按目录顺序覆盖。 |
| I04 | manifest 原始字节及全部纳入的资源均参与锁；版本不变不意味着内容未变。 |
| I05 | 审核消费固定 ResourceRef；不重新跟随可变名称、当前锁别名或当前 profile。 |
| I06 | 03 仅消费通用资源引用和当前守卫；插件具体字段由 06 验证，不在审核层执行插件逻辑。 |
| I07 | 检查前固定与执行时使用同一组内容；不能“验 A、读 B”，也不把二次 stat 称为多文件原子快照。 |
| I08 | 插件只能提出需求；缺权限或能力就阻塞，不自动提高授权、换 CLI、降级模型或跳过必要检查。 |
| I09 | 平台覆盖按整个声明集合验证；依赖支持的范围不足时阻塞，不静默取交集缩小承诺。 |
| I10 | 新锁、新审核、新运行追加记录；不修改历史 attempt、原始日志、旧锁或旧 verdict。 |
| I11 | 文件哈希证明内容完整性，不证明来源可信、代码无害、权限充分或审核者身份。 |
| I12 | 阶段成功不能提前产生 PASS：`RESOLVED`、`SEALED`、`REGISTERED` 都不是候选验收结论。 |

### 1.4 保证等级与威胁模型

| 场景 | 首期可提供的控制 | 不能自行声称的保证 |
|---|---|---|
| 可信维护者误编辑、资源遗漏、普通漂移 | 严格 Schema、精确依赖、完整字节清单、重新核验 | 不保证配置业务语义正确 |
| 模型/插件输出试图扩大权限 | 核心允许字段投影、显式权限交集、独立检查 | 提示词分隔符不是 OS 沙箱 |
| 非受信文件试图被自动加载 | 禁止扫描/远程获取、闭包内资源代理 | 不能约束仍能任意读文件的第三方 CLI |
| 同账户进程恶意修改目录/核心/账本 | 需要受控文件存储、隔离权限、受信启动环境 | 单进程 Python 校验不是对同账户攻击者的完整隔离 |
| 管理员、内核、宿主失陷 | 不在本模块保证范围；保留审计边界 | 本地普通哈希不是抗宿主篡改证明 |

## 2. 依赖与输入输出

### 2.1 模块分工

原文前置依赖为 02 配置、03 审核与锁定、05 平台执行；公共引用遵循 01。04 提供角色所需的真实 runtime 能力证据，07/08 消费任务类型、步骤及检查。[^P06]

| 模块 | 负责内容 | 06 不得替代 |

| 06 | 清单、依赖、资源闭包、锁与声明式编译输入 | 准入、预算扣账、发布合同、门禁 PASS |
| 07 | 工作流/DAG 执行、重试、预算、步骤与检查编排 | 把插件加载拓扑顺序直接当成执行 DAG |
| 08 | 首批真实业务插件与业务场景验收 | 把本版合成插件当成业务插件已交付 |

### 2.2 输入、输出与信任归属

| 对象 | 最少内容 | 来源与使用规则 |
|---|---|---|
| `EnabledPluginSelection` | 精确 `id/version` 列表 | 02 已校验配置；不是磁盘扫描结果 |
| `TrustedPluginCatalog` | ID、允许版本、仓库相对根、相关信任登记引用 | 受保护核心装配；调用者不能自行构造“可信”标签 |
| `PluginManifest` | 类型、兼容、资源、步骤、检查、依赖、权限 | 未受信数据，严格解析后才进入模型 |
| `ResolverPolicy` | Schema/编译器版本、路径/模板/Schema 策略、限额 | 可信核心固定资源，规则变化影响解释结果 |
| `CapabilityEvidence` | 平台/角色、能力、版本、来源、限制 | 04/05；无证据就标 unknown，不回填 |
| `AuthorizationContext` | 用户、项目、角色、合同的范围及当前守卫 | 03/现行授权系统；不是插件生成 |
| `ResolvedPluginSet` | 精确节点、边、导出句柄、完整资源清单、诊断 | 06 候选输出；还不能运行 |
| `PluginLock` | 固定清单、排序、逐文件字节哈希、核心解释依赖 | 调度器生成、封存；文件自身不含自身哈希 |
| `PluginCompileReceipt` | 锁引用、输入/输出字节引用、编译器引用、目标角色/平台 | 06 编译层生成；不等于审核回执 |
| `LockPublicationReceipt` | 操作 ID、范围、generation、锁引用、提交事实 | 受控发布层；与内容确定性分开 |

### 2.3 公开接口建议

```text
parse_manifest(raw_bytes, manifest_schema_ref, limits) -> Manifest | Diagnostics
resolve_plugins(enabled, trusted_catalog, fixed_policy, source_reader) -> ResolvedPluginSet
validate_resource_bundle(resolved, offline_schema_registry, command_validator) -> ValidationReport
seal_plugin_inputs(resolved, controlled_store) -> SealedPluginInputs
build_plugin_lock(sealed_inputs, core_refs) -> PluginLockBytes
publish_plugin_lock(lock_ref, expected_generation, operation_id) -> PublicationReceipt
verify_plugin_inputs(lock_ref, fixed_selection, current_bindings, current_policy) -> VerifiedPluginInputs
preflight_plugin_requirements(verified, capability_evidence, auth_context) -> GapReport
compile_plugin_task(verified, selected_step, input_ref, target_context) -> CompileReceipt
```

解析、依赖求解与预检不启动 CLI、不执行插件命令；受控读取文件不等于允许插件自定义读取逻辑。`verify_plugin_inputs` 的成功结果只能用于本次受控消费范围，不是永久布尔缓存。

`publish_plugin_lock` 是**建议新增接口**，不是声称当前 dispatcher 已有该子命令。本文中的接口名、SQL 表名均须在实施时与实际仓库协调。

### 2.4 端到端数据流

```text
02 固定启用项 + 受信目录映射 + 解释规则
                  ↓
06 严格解析 → 精确依赖图 → 资源清单/Schema/检查静态验证
                  ↓
受控快照与字节封存 → 确定性 PluginLock → 独立发布回执
                  ↓
合同/草稿生成方纳入 lock_ref、输入、编译结果、检查定义 → 冻结合同字节
                  ↓
03 审核通用 input_refs（不导入插件模块执行声明）
                  ↓
prepare/run：03 当前守卫 + 06 完整性/绑定核验 + 04/05 能力与环境核验
                  ↓
07 编排 → 04 构造 Invocation / 核心固定检查 → 05 执行
                  ↓
原始证据 + 输出类型校验 + 独立检查 + 既有 G0–G6
```

## 4. 接口和行为约束

### 4.1 Manifest 最小内容

#### 4.1.1 版本轴、类型与首期收口

| 版本轴 | 建议字段/规则 | 不可混同 |
|---|---|---|
| manifest 结构 | `schema_version: 1` | 该记录家族首版，不是合同 schema v1 |
| 任务插件 API | `api_version: 1`，整数、显式精确匹配 | 不靠插件软件版本推导 API |
| 插件内容发布版本 | `version`，精确 SemVer 字符串 | 不以排序相等代替精确身份 |
| 锁结构 | `record_type=plugin_lock`，`schema_version:1` | 不与 manifest 共用未知版本回退 |
| 编译/解析规则 | 固定 `resolver_profile` 与 `core_refs` | 不只记录一个人类可读“v1”字符串 |
| 平台/CLI/模型 | 04/05 环境和能力记录 | 插件不能自行宣布实际运行版本 |

新增建议采用 SemVer 2.0.0 语法，但**依赖匹配使用完整字符串相等**，包括预发布和 build metadata。SemVer 对版本优先级比较会忽略 build metadata；本模块不是在做优先级求解，所以 `1.0.0+build-a` 与 `1.0.0+build-b` 不可互换。[^R01]

首期不接受 `^1.2.0`、`~1.2`、`latest`、`*`、分支名、Git revision 或省略 patch。允许预发布版本不等于自动信任预发布；信任目录必须明确允许该完整值。API 版本未知、manifest 类型不是 `task` 时立即拒绝，不调用“最接近”的解析器。

#### 4.1.2 字段级契约

以下完整记录形状见附录 A。为了避免默认值在不同实现间漂移，首版建议所有表列字段必填；没有条目使用空数组，不接受 `null`。这比原文的字段组更具体，属于新增设计。

| 字段 | 类型/约束 | 关键语义 |
|---|---|---|
| `schema_version` | 整数，精确为 1 | 不接受布尔或 `1.0` 形式的版本字段 |
| `id` | 小写 ASCII 标识，最长 64 字符 | 禁用保留 ID `core`、`codekit`；目录名不代替身份 |
| `version` | 最长 96 字符的精确版本 | 原字符串保留；不自动 trim、补零或去后缀 |
| `api_version` | 整数，精确为 1 | 单独 API 校验 |
| `type` | 固定 `task` | 无任意代码加载类型 |
| `platforms` | 非空、去重的 `linux/macos/windows` 数组 | 声明全部支持面，不只是当前机器 |
| `roles` | 非空、去重的 planner/executor/observer | 首版不允许插件提供 supervisor |
| `requires_capabilities` | `{role,id}[]` | 使用 04 已登记能力 ID，按角色检查 |
| `input_schema` / `output_schema` | 本插件 schema 资源 ID | 引用种类必须是 schema |
| `resources` | `{id,path,kind}[]` | 明确文件清单；不接受 glob、目录、URL |
| `steps` | `{id,role,template,input_schema,output_schema,needs}[]` | 声明步骤；真正执行由 07 编排 |
| `checks` | `{id,definition,after}[]` | definition 指向 check 资源；required 等共同语义留在 05 命令定义 |
| `dependencies` | `{id,version}[]` | 全部必需、精确版本；无自动 optional/fallback |
| `conflicts` | 插件 ID 数组 | 任一方向声明互斥即拒绝共同组合 |
| `permissions` | `{action,scope}[]` | 需求，不是授权；scope 由核心注册和绑定 |
| `exports` | `{id,kind,target}[]` | 显式可消费句柄；不注入全局同名符号 |

不接受 `_comment`、`_note` 等额外字段。02 的配置说明字段例外不能延伸到 manifest/lock；重复键在解析阶段就拒绝，不能让 JSON 解码器保留最后值后再校验。Python 默认解析行为需要通过显式钩子收紧。[^P02E][^R02]

`required/default/format` 的语义不能靠字段名猜测。JSON Schema 的 `default` 是注解而非自动填值命令；format 是否断言取决于采用的词汇和实现策略。本版业务 Schema 子集不开放任意 format 或自定义 Python 校验器。[^R04]

#### 4.1.3 资源类型与可执行内容边界

| `kind` | 载荷 | 允许解释阶段 | 禁止行为 |
|---|---|---|---|
| `schema` | UTF-8 严格 JSON | 受限、离线 Schema 验证器 | 外部获取、动态 Python format、任意 schema vocabulary |
| `template` | UTF-8 文本 | 固定版本声明式渲染器 | `eval`、函数调用、文件 include、环境读取、网络访问 |
| `check` | 05 检查定义 JSON | 核心 CommandSpec 校验与后续合同编译 | 解析期间执行、自动探测安装工具 |
| `data` | 明确使用的原始字节 | 核心资源代理按受审用途提供 | 按文件后缀猜测可执行代码或自动展开压缩包 |
| `check-script` | 作为数据锁定的受审脚本 | 仅在正式命令与准入后，由 05 外部 runner 执行 | 作为调度器模块 import，或加载时运行 |

声明式插件可以携带“将来由 runner 执行的检查脚本”，不等于允许调度器进程加载可执行插件。脚本及实际依赖必须被锁定；本版离线参考不会执行脚本，也不证明任意脚本的 import 闭包完整。

首期建议所有 manifest 声明资源都纳入锁，即使某资源只供某平台、某可选工作流分支使用。这是**保守闭包策略**：易于解释、避免漏锁，但同一插件内声明而未执行的资源变化也会使该插件锁变化。未来要按步骤裁剪闭包，必须升级解析规则并重新验证，不能临时删除“看起来没用”的文件。

#### 4.1.4 显式启用与受信目录

采用两步解析：02 指定启用根插件；可信目录为根插件及传递依赖提供 `(id,version) → repository_relative_root` 映射。传递依赖可以不列在顶层 enabled 中，但必须被同一信任策略明确允许，且具备可追溯来源。

| 情况 | 建议行为 |
|---|---|
| 根插件未在 enabled 中 | 不加载；磁盘上存在不改变结果 |
| 依赖被声明，但信任目录没有该精确版本 | 报依赖链及信任缺口；不搜索其他目录/网络 |
| 相同 ID 在两个可消费根中出现 | 拒绝；不按目录优先级选择 |
| 目录映射与 manifest 的 id/version 不符 | `E_PLUGIN_IDENTITY` |
| 目录映射或信任状态在审核后改变 | 当前绑定/授权校验失败，按 03 重新处理 |
| 无关插件的目录/版本改变 | 不应影响当前已选择闭包，除非共同策略确实变化 |

首版参考目录每个 ID 只保留一个精确候选。未来一个 ID 存多个已信任版本时，可以扩展目录索引为 `(id,version)`；解析集合内仍不得同时出现同 ID 不同版本。

信任记录属于受保护管理面，不能由 `trusted:true`、仓库作者名、版本字符串、签名字段的存在或 planner 自述形成。采用签名/外部供应链证明是后续可选设计，还需密钥、撤销、发布主体与目标项目策略；本版不实现。

#### 4.1.5 精确依赖图算法

图节点使用插件 ID，节点值绑定唯一版本；有向边 `A → B` 表示 A 需要 B。遍历时分别维护“请求版本”“访问颜色”“第一条来源链”，避免把版本冲突错误归类为循环。

```text
输入：固定 enabled 集合、受信目录、解析策略、资源上限
1. 检查 enabled 自身重复/版本格式，按 ID 排序。
2. 对每个根执行 visit(id, exact_version, dependency_chain)。
3. 同 ID 已存在且版本不同：返回两条请求链和 E_PLUGIN_VERSION_CONFLICT。
4. 未登记的精确来源：返回 E_PLUGIN_NOT_TRUSTED，不联网或枚举候选。
5. 从固定来源读取 manifest；严格 Schema 与身份校验。
6. 对声明的直接依赖按 ID 排序访问；达到节点/深度上限立即失败。
7. 依赖图完成后，检查循环；错误给出构成环的链。
8. 检查任一方向 conflicts、命名空间、平台与角色要求。
9. 生成依赖先于使用者的稳定拓扑序；独立节点按 ID 确定次序。
```

`A→C@1.0.0` 与 `B→C@1.0.0` 是正常菱形共享，C 只收集一次；`B→C@2.0.0` 则冲突。`A→B→A` 为循环；两插件一方声明互斥就足以拒绝。不把缺依赖当作“这个步骤可能不会执行”。

稳定拓扑序用于确定编译输入与可复算诊断，不定义 07 的调度并行性、执行次数或数据依赖。复杂度在没有排序时约为节点加边；稳定排序成本单独计算，资源字节读取和 Schema 验证通常另计。

#### 4.1.6 平台兼容与角色能力

**组合兼容**不是简单给出平台交集后继续：对根插件每个声明支持的平台，所有所需依赖和检查都必须存在实现。只有实施合同明确采纳的新版本 manifest 才能缩小支持范围。

角色要求必须在插件、所选角色/profile 与目标运行环境三者中一致。能力证据按 04 的版本、平台、来源与限制匹配；帮助文本或配置值不自动算实测。缺 `model_identity`、必要工具事件或输入通道能力时，不自动换 CLI/profile。[^P04]

静态预检只能消费已有能力记录或输出“需要 04/05 探测”的计划。06 不能因为函数名叫 `validate` 就在里面运行 `--version`、登录、安装或刷新模型清单。

#### 4.1.7 命名空间与导出

建议完整句柄为：

```text
plugin:<plugin_id>/<kind>/<export_id>
```

句柄解析后固定：`plugin_id + exact_version + lock_ref + target_resource_or_step + schema_ref`。逻辑句柄本身不是授权凭据，运行时不得重新跟随同名插件。

同插件导出 ID 必须唯一；跨插件同名可以通过命名空间并存。显式业务别名若重复就报错，不按加载顺序覆盖。核心检查保持独立命名空间，例如 `core:G0`；插件的 `plugin:review/check/report-json` 无权改写它。

输入/输出的“类型相容”首版建议使用固定 schema 资源身份与编译声明进行精确匹配，不实现任意 JSON Schema 的逻辑蕴含求解。类型转换必须作为明确、锁定、受审的步骤；不能因两 schema 都是 object 就认为可以直接互接。

#### 4.1.8 离线 Schema 引用闭包

JSON Schema 的 URI 是标识，不必可下载；`$id` 改变引用解析基准，`$ref` 不是普通文件字符串。因此不能只找出 JSON 中的 path 字段就认为闭包完整。[^R03]

建议首版采用受限策略 `bounded-offline-schema-v1`：

| 项目 | 首期规则 |
|---|---|
| dialect | 固定 Draft 2020-12；官方 meta-schema 由核心离线注册 |
| 插件 Schema 身份 | 核心根据精确插件 ID/版本/资源 ID 生成受控 URI |
| 本文件引用 | 支持 JSON Pointer fragment，例 `#/$defs/topic` |
| 跨文件/跨插件 | 仅受控 registry 中的精确 URI；跨插件必须声明直接依赖 |
| 网络/file URI | 拒绝自动解析；未知 URI 即失败 |
| `$id/$anchor/$dynamicRef` 等扩展 | 首期不支持，显式拒绝，不静默忽略 |
| 自定义关键词、正则、format 扩展 | 首期参考子集拒绝；扩展时另设版本、性能和安全边界 |
| 引用循环/递归 Schema | 首期建议拒绝，避免无界递归；不声称完整支持所有合法 2020-12 Schema |
| 未被业务分支使用的 `$defs` | 仍静态检查闭包，不能藏未登记引用 |
| 注解或 const 内的 `{"$ref":...}` 数据 | 按 Schema 语义位置处理，不误当引用 |

URI 例：`urn:codekit:plugin:shared:1.0.0:input#/$defs/topic`。它不是下载地址。为防止歧义，首版片段仅允许已支持的 JSON Pointer 形状，不接受未实现的 URI percent 编解码。JSON Pointer 的 `~0/~1` 必须按标准次序解释，不能做任意字符串替换。[^R11]

受控 Schema registry 只登记封存且哈希核验的对象；缺 URI 时的 retrieve 回调直接拒绝。`referencing.Registry` 可实现这种离线注册，不能顺手增加 HTTP 兜底获取。[^R05]

必须分开验证：manifest Schema 约束 manifest 的未知字段；插件数据 Schema 本身的 meta-validation；受限词汇/引用闭包；实际输入/输出实例的验证。这四项任何一项失败都不能报告为完整通过。

#### 4.1.9 模板闭包与确定性编译

建议首版模板仅支持 `{{input.FIELD}}`，FIELD 为已批准输入 schema 下的单层字段名。替换使用 JSON 编码后的值，不递归解释替换结果。其余模板表达式、include/import、环境变量、时间/随机数、文件读取、网络与函数调用全部拒绝。

模板只渲染角色请求的**数据部分**，不能用于 shell/script/argv 的通用字符串拼接。模型可读的请求文本要附来源、用途、锁引用和权限说明，但提示分隔符不提供 OS 隔离，也不能彻底消除提示注入风险。

建议编译回执包括：

| 字段 | 含义 |
|---|---|
| `plugin_lock_ref` / `compiler_ref` | 固定锁及解释代码/策略 |
| `step_handle` | 固定插件版本下的步骤 |
| `input_ref` / `input_schema_ref` | 已校验的输入字节与 schema |
| `selected_role` / `target_platform` | 02/05 提供的目标 |
| `rendered_request_ref` | 实际生成并冻结的请求字节 |
| `check_set_ref` | 核心验证后生成的检查定义集合 |
| `resource_bindings` | 原模板/资源到消费对象的映射 |
| `diagnostics` | 缺字段、超限等结果；不得附凭据 |

正文包含敏感业务数据时，按既有数据处理与脱敏政策保存；不能在公开日志里打印渲染结果。请求正文、最终命令和环境事实的存储位置及权限由核心分配。

#### 4.1.10 隐式输入与禁止自动发现

只允许资源代理按锁内 ID 读取内容，不传给模板一个任意 `Path`。禁止把整个插件根目录作为 CLI 可自动扫描的资源目录，也不自动生成 Pi skills/extensions 配置。外部 CLI 仍可能读取 cwd/HOME/settings 等隐式输入，其禁用和精确绑定由 04/05 验证，不能由 06 假定。[^P04]

检查脚本若 import 同目录辅助代码、加载配置、调用系统工具或读取环境，这些都会影响行为。首期真实业务插件必须显式清单化依赖，或使用已锁定、已审核的工具环境；纯静态字符串分析不能证明任意 Python/JavaScript 程序的全部动态依赖。

新增未列出的磁盘文件不会自动进入锁，也不应影响当前闭包；但是**一旦任何消费路径尝试读取该文件，必须返回闭包外读取错误**。新增 manifest 条目、模板 include 或 loader 行为改变则必须改变锁或解析规则，拒绝旧审核。

#### 4.1.11 输入与计算限额

以下是待压测的首版建议初值，不是性能实测或平台上限：单 JSON 1 MiB，单资源 8 MiB，组合资源 64 MiB；插件数 128；每插件显式资源 512；依赖深度 64；Schema 图节点 10,000；JSON 嵌套 64；渲染结果 1 MiB。整数限制与 01 当前公共规则协调。

字节、节点、深度和渲染限额都要在分配/读取过程中检查，不能只靠文件 stat 大小。解析或验证墙钟时间上限由核心受控 worker 实现；同步调用后才检查耗时不能中止已经卡住的验证器。参考代码验证结构上限，不实现生产级 CPU/内存隔离。

#### 4.1.12 错误分类与诊断稳定性

沿用 01 的 `code/message/details/retryable`。建议 details 包含安全插件 ID、JSON Pointer 字段位置、来源 ResourceRef、依赖链、期望/观察到的非敏感身份及恢复方向；避免原始 exception 把完整文档、绝对路径或凭据打印出来。

| 错误组 | 典型原因 | 可恢复方向 |
|---|---|---|
| `E_MANIFEST_*` | 缺字段、未知字段/API/type、版本类型非法 | 修订 manifest 并重新锁定 |
| `E_PLUGIN_VERSION*` | 范围版本、精确版本冲突 | 显式统一依赖版本，不自动求解 |
| `E_PLUGIN_NOT_TRUSTED` | 未登记根/依赖 | 受信管理流程，不自动启用 |
| `E_PLUGIN_CYCLE/CONFLICT` | 环或互斥 | 修改组合，保留冲突链 |
| `E_PLUGIN_PATH* / FILE_*` | 路径、链接、类型、读取或限额问题 | 修复来源和边界，不关闭校验 |
| `E_SCHEMA_*` | 外部引用、未支持关键词、循环、类型 schema 损坏 | 收敛到支持子集或另行扩展政策 |
| `E_TEMPLATE_*` | 表达式、输入缺失、编码、超限 | 改受控模板/输入，不启用 eval |
| `E_CHECK_*` | 覆盖不足、结构/绑定冲突、核心检查覆盖 | 修正检查定义并重审 |
| `E_LOCK_*` | 清单差异、哈希漂移、未封存、CAS 冲突 | 重新构造或恢复精确字节 |
| `E_PLUGIN_CAPABILITY/PERMISSION` | 能力/授权缺口 | 缩小任务或按既有授权处理；不自动重试付费调用 |

上述错误家族是拟议注册项，不能与 01 已有错误码碰撞。多故障输入不承诺各实现同一第一错误；单一故障夹具应稳定定位。底层只知道 `OSError` 时报告安全读取错误，不凭空判断它一定是越界链接。

### 4.2 内容锁定

#### 4.2.1 何为完整锁定对象

原文要求锁定 manifest 和实际使用的 schema、模板、检查定义、资源，而非仅版本字符串；新增加载项、缺失和字节变化都要阻止旧审核消费。[^P06]

本版保守策略把闭包定义为：

```text
顶层 enabled 精确集合
  + 根插件及全部传递依赖的 manifest 原始字节
  + 所有选中 manifest 声明的资源原始字节
  + Schema/模板/检查跨资源引用所需且已声明的目标
  + 核心 manifest Schema、编译器/解析器及其政策的固定引用
  + 另行审核绑定的相关配置、信任登记、环境、业务输入与检查集合
```

最后一行不是必须都塞进 PluginLock。锁负责插件内容，03/合同负责完整审核输入闭包；资源引用不能遗漏，但也不应为了方便把全仓库所有 profile、信任记录、进度事件都作为一个大依赖，导致无关任务连带失效。

每个被读取的插件资源有 `(plugin_id, resource_id, source_relative_path, kind, size_bytes, sha256)`。一个路径只登记一次；若不同用途确实需要同一字节，通过同一个资源 ID 引用，不创建加载顺序别名。

#### 4.2.2 路径规则与三平台差异

沿用业务路径为仓库相对、正斜杠格式；插件资源 path 相对插件根。原文已拒绝绝对路径、`..`、解析后越界链接及 junction。[^P01][^P06]

本版建议 `portable-nfc-no-links-v1` 进一步收紧，必须明确这是新增限制：

| 项目 | 建议检查 |
|---|---|
| 词法 | 拒绝空路径/空分段、`.`、`..`、反斜杠、NUL、绝对路径、drive/UNC/device 形式 |
| 字符 | 拒绝控制/格式字符、Windows 禁用字符；首期不做 percent 解码并拒绝 `%` |
| 尾部/保留名 | 拒绝末尾点/空格和保留设备名，包括带扩展名形式 |
| Unicode | 路径必须已为 NFC，不自动改写；资源**内容**不做 Unicode 归一化 |
| 别名碰撞 | 对完整路径及每一级目录前缀做保守 casefold 冲突检查 |
| 类型 | 只读普通文件；拒绝目录、FIFO、socket、device |
| 链接 | 首期拒绝全部插件路径中的 symlink/reparse/junction，包括仍指向根内的链接 |
| 硬链接 | 首期源文件 link count 大于 1 时拒绝，避免共享 inode 的外部写入口 |
| 根目录 | 受信目录不能重复/相互嵌套；必须基于已固定仓库根验证 |

Windows 对文件名、设备名、路径命名空间有专门规则；不能把 Linux 上字符串校验通过当成 Windows 原生路径已经验证。reparse point 和 hard link 的语义也不同，不能只检查 `is_symlink()` 就宣布全部覆盖。[^R06][^R07][^R08]

casefold/NFC 是本版保守冲突筛查，不是完整仿真 NTFS/APFS 的名字比较；仍要进行目标文件系统实测。原名无法在首版政策下使用时，返回改名建议，不能静默将两个资源重命名成同一文件。

#### 4.2.3 安全读取、句柄固定与一致性上限

生产实现按平台提供 SourceReader：先固定受信仓库/插件根句柄，再逐级受控打开，拒绝链接/特殊文件；以同一打开对象读取并计算摘要。POSIX 可利用 `dir_fd`、`O_NOFOLLOW` 等能力；具体可用性须检查。Windows 应由原生句柄与 reparse/file identity 校验实现，不声称 `resolve()` 后再 `open()` 就解决了竞态。[^R09]

读取前后的 file identity、size、mtime/ctime 可用于发现常见并发修改，但不能证明恶意写入未发生，也不能保证多文件来自同一个瞬间。普通文件的“只读权限”不阻止有权改权限或同账户写入者。

**首选生产路径**：受控发布者生成不可变源版本，或从固定 Git tree/受控快照取得字节；再复制到核心持有的内容库。选择 Git tree 时明确锁的是对象中的字节，不自动等同于 checkout 工作树字节；Git attributes 可能在 checkout/checkin 时转换内容。[^R10]

不具备不可变源版本时，使用受控读写协调和前后重核验，记录只能检测已观察漂移的保证上限。若正式安全要求必须获得一致快照，而环境不能提供，拒绝正式派遣；不能用“连读两遍一致”冒充强快照。

#### 4.2.4 源字节、存储字节与消费字节

建立三方对应：

| 对象 | 作用 | 核验 |
|---|---|---|
| `source` | 被信任目录指向的声明资源 | 来源身份、版本、当前绑定及完整字节 |
| `sealed object` | 调度器控制的固定副本 | 写入完整、逐字节 hash、无共享可变链接 |
| `consumed object` | 编译器/runner 实际读取内容 | 来自封存对象或同一受控句柄，不重开可变来源 |

不能用 hard link 把源直接“快照”到存储库，因为两名称仍指向同一可修改文件内容；原子复制/文件发布和链接关系应分别判断。[^R08]

日志、模型正文、生成报告与临时文件绝不反向进入插件源目录。编译输出另行封存；运行输出也不能成为原插件输入，除非显式定义新的输入版本并重新审核。

#### 4.2.5 清单排序、序列化与哈希

锁引用遵循 `ResourceRef={kind,id,sha256,path}`；`sha256` 为完整文件字节摘要，文件内不写自己的摘要。每个源文件以原始字节计算；修改一字节、换行或编码变化均改变它的摘要。[^P06]

为了生成确定的锁文件，本版**建议复用 01 的核心生成字节函数**，不提出第二套 JSON canonicalization。这里是为新增 PluginLock 选定生成编码，不是把任意外部 manifest 转成“语义相等”再哈希：

```python
(json.dumps(value, ensure_ascii=False, sort_keys=True,
            separators=(",", ":"), allow_nan=False) + "\n").encode("utf-8")
```

| 数组/字段 | 建议顺序与处理 |
|---|---|
| enabled | 按插件 ID 排序；重复输入拒绝，不隐式去重 |
| plugins | 按 ID 排序；单 ID 唯一精确版本 |
| dependencies | 按 ID 排序；重复/冲突拒绝 |
| files | 按 path，再按 resource ID；重复/碰撞拒绝 |
| core_refs | 按 kind、id；同逻辑资源冲突拒绝 |
| load_order | 稳定拓扑算法输出；依赖先于使用者 |
| manifest 内原始数组 | 不改写源文件；即使重排业务等价，原字节变化仍导致新摘要 |
| timestamps、host、临时路径、publication generation | 不放入内容锁；进入独立发布/环境记录 |

相同源字节、启用集合和核心解释规则应生成相同锁字节。换加载遍历顺序不能改变结果；改变 manifest 的空格/行尾则应改变文件摘要。该规则不是 RFC 8785/JCS，不自动重写历史锁或历史输入。[^P01]

#### 4.2.6 锁文件结构与自引用防护

附录 A 给出完整 `PluginLock` Schema，附录 B 的 `sample.plugin-lock.json` 由实际合成字节生成，无占位摘要。结构包括：记录版本、解析/路径/Schema/模板策略、`core_refs`、enabled、plugins、load_order。

锁内容不含 `approved`、`locked:true`、`verdict`、`recorded_at` 或自身 SHA-256。`core_refs` 绑定实际参与解释的 schema/编译器资源，防止“文件未变但解释规则变了”仍复用旧锁。

依赖方向必须是：插件源/核心规则 → 插件锁 → 编译结果/合同 → 审核 → 运行/验收。审核文件不反向塞进插件锁；插件 manifest 不引用包含其自身 hash 的锁。出现资源依赖环时拒绝，不用空 hash 临时回填。

#### 4.2.7 当前锁、不可变版本与发布回执

保留原文 `.agent/plugins.lock.json` 作为**当前内容锁的完整 JSON 投影**，不悄悄改成另一种指针格式。新增建议同时保存不可变历史版本，例如 `.agent/plugin-locks/<sha256>.json`；正式审核/合同应引用不可变版本，而非未来可能被替换的当前投影。

| 层 | 建议对象 | 性质 |
|---|---|---|
| 内容存储 | 封存资源对象、不可变锁文件 | 字节固定，可被多个引用 pin |
| 发布账本 | scope、operation、lock_ref、generation、提交时间 | 受控追加与 CAS，不回填内容锁 |
| 当前投影 | `.agent/plugins.lock.json` | 便于查看和新规划；不是旧审核重新绑定入口 |
| 历史运行 | attempt 固定副本/引用及既有 pin | 不被新发布覆盖 |

若未来正式实现选择“当前锁文件自身作为可变绑定资源”，也必须在审核前复制冻结并保留旧字节；不能持有旧 hash 却继续读被覆盖路径。原文没有决定发布账本形态，本节是用于消除歧义的建议。

本次不会在目标项目创建这些路径。合成锁保存在验证包中的 `sample.plugin-lock.json`。

#### 4.2.8 发布状态机与确定的提交点

```text
RECEIVED → RESOLVED → SOURCES_FIXED → OBJECTS_SEALED → LOCK_SEALED
                                                       ↓
                                              REGISTERED（账本提交点）
                                                       ↓
                                              PROJECTION_SYNCED
```

解析或封存失败进入 `REJECTED`；封存完成但未登记的对象为 `ORPHANED` 候选；客户端不知道登记是否成功为 `UNKNOWN_COMMIT`，需按 operation_id 查询。`LOCK_SEALED` 不是审核通过，`PROJECTION_SYNCED` 也不是可直接执行。

发布次序建议：固定源版本与当前绑定 → 创建本次 staging/build lease → 写入并核验资源 → 发布不可变对象 → 生成并封存 lock → 在事务中核对相关 generation、登记发布、建立 pins、更新 head → 提交 → 同步当前投影。

`os.replace` 可用于相应平台支持的文件替换，但并不提供“仅当 head 仍是旧值”的比较并更新，也不使数据库与文件系统成为一个事务。需要单独处理 CAS、同步与断电持久性。[^R09]

新锁失败时保留旧有效锁；不要先删旧锁再创建新锁。不可变目标已存在时，验证其完整 bytes/hash；不同内容冲突即拒绝，不能覆盖。

#### 4.2.9 并发发布与幂等事务

建议发布请求绑定：`operation_id`、`scope_id`、`expected_generation`、`candidate_lock_ref`、相关 source/trust binding versions、调用主体与固定请求摘要。scope 表示受控的启用组合绑定，不用文件路径或随机 run ID 代替其逻辑身份。

以下为**事务算法示意**，不是实际项目已存在的 SQL。`assert_rowcount` 和权限检查由服务实现；表名在正式迁移时确定。

```sql
BEGIN IMMEDIATE;
-- 1. 查询 operation_id：相同请求摘要返回已有登记结果；摘要不同拒绝。
SELECT intent_sha256, generation, lock_sha256
FROM plugin_lock_publish WHERE operation_id = :operation_id;

-- 2. 核对相关 source/trust bindings 及发布权限，不把客户端值当权威。
-- 3. 已封存对象通过受信核验后，登记对象与本次引用/pin。
-- 4. scope 首次创建只能由明确 create 路径完成；普通更新要求旧 generation 相符。
UPDATE plugin_lock_head
SET lock_sha256 = :new_sha256, generation = generation + 1
WHERE scope_id = :scope_id AND generation = :expected_generation;
-- assert_rowcount == 1，否则 ROLLBACK 并报告 E_LOCK_CAS。

INSERT INTO plugin_lock_publish
(operation_id, intent_sha256, scope_id, generation, lock_sha256)
VALUES (:operation_id, :intent_sha256, :scope_id,
        :expected_generation + 1, :new_sha256);
-- 在同一事务内登记 publication/approval 所需 pins 和 outbox。
COMMIT;
```

SQLite `BEGIN IMMEDIATE` 会尝试立即取得写事务，遇到其他写事务可能返回 busy；业务层须采用有界重试，并在每次重试中重新读取 head/守卫。它不是对外部文件写入或另一授权服务的分布式锁。[^R12]

两个并发发布者使用同一 expected generation，最多一个成功；失败者不能“更新 expected 后不重核输入”直接覆盖。相同 operation 重试在当前授权允许查询的前提下返回原登记事实，不再次推进 generation。返回原事实不证明原锁现在仍可用；当前有效性另行核验。

#### 4.2.10 文件/账本补偿与持久性

| 故障窗口 | 可能残留 | 必须行为 |
|---|---|---|
| 资源写到一半 | staging 临时文件 | 不可引用；记录失败/lease，不当作资源 |
| 资源封存后、lock 未完成 | 无引用对象 | 可保留待 GC；不推导发布成功 |
| lock 封存后、事务前 | 完整孤儿 lock | 原 operation 重新核验后可登记；不得后台自动批准 |
| CAS 失败 | 旧 head + 新孤儿内容 | 回滚所有元数据；旧锁继续有效 |
| 事务提交、响应丢失 | 已登记但调用者未知 | 查询 operation；禁止重复发布产生矛盾事实 |
| 事务成功、当前投影写失败 | head 正确、投影滞后 | 标记 `PROJECTION_STALE`；按账本重新生成投影 |
| 账本有引用、对象丢失 | 悬空证据 | 阻塞消费；维护授权下恢复完全相同 bytes |
| 存储空间/权限不足 | 不完整 staging/失败状态 | 不切换 head；输出可执行修复方向 |
| 旧备份恢复覆盖新撤销事实 | 内容看似完整，控制面过时 | 恢复隔离，核对可信高水位与当前授权，不能直接启动 |

fsync 文件、目录同步、rename 原子可见性、数据库提交持久性分别记录；不以 mock 或单次正常退出证明断电可恢复。跨文件系统移动不能假定原子；网络盘、同步盘和不同 OS 后端均需独立测试。

#### 4.2.11 prepare/run 的完整验证顺序

建议所有消费入口共用下列服务，不各自裁剪：

1. 读取并验证 03 审核、主体/动作范围、当前撤销与受控绑定；v2 不走隐式 v1 分支。
2. 解析固定 lock_ref，核验定位合法、完整 bytes/hash、记录家族和 Schema。
3. 核验 core_refs 与解析政策；不使用未锁定的新 parser 解释旧锁后声称等价。
4. 从固定 enabled 与受信来源重建期望依赖/资源集合；集合必须精确一致，额外项与缺失项都拒绝。
5. 核验全部封存对象、当前相关来源/绑定、精确版本、互斥与命名空间。
6. 核对所需平台/角色、04/05 能力证据、项目保护路径与当前权限。
7. 核验实际输入/编译结果/正式检查命令引用，固定将被消费的对象句柄。
8. 与 03/07/05 完成当前准入和 handoff；不把插件校验结果单独作为启动许可。

验证不能只读 `plugins.lock.json` 并逐条相信其中的清单，否则攻击者可能删除条目后重算一个自洽 hash。审核固定摘要可以防止未授权 lock 替换；完整性服务还应从受信输入重建清单以发现伪造/错误生成的候选。

参考代码中的 `verify()` 演示固定 hash、Schema 和重新求解后的字节比较，**不实现步骤 1 的真实审核/授权，也不提供启动准入**。

#### 4.2.12 漂移、ABA 与精确失效

| 变化 | 是否影响插件锁/审核 | 处理 |
|---|---|---|
| 已声明 manifest/schema/template/check 任一字节变化 | 是 | 新锁/新审核；版本未变也拒绝旧输入 |
| 新增 manifest 资源或依赖 | 是 | 重算闭包，禁止旧审核沿用 |
| 新增从未声明且从未读取的磁盘文件 | 当前保守闭包不受影响 | 不自动发现；若尝试消费则拒绝 |
| 同插件已声明但当前步骤未用资源变化 | 首期保守策略下是 | 明确这是锁粒度取舍，不偷偷按步骤裁剪 |
| 未启用、非传递依赖插件变化 | 否，除非共同受审策略改变 | 精确限制依赖范围 |
| 解析器、manifest Schema、模板政策变化 | 是 | 核心规则 ref 改变，重新验证/审核 |
| 移动相同字节的插件根 | 至少需新合法定位及绑定 | 不只凭 hash 相同自动复用 |
| 信任撤销、权限收窄、环境变化 | 内容 hash 可能不变，但当前准入变化 | 03/04/05 守卫负责阻塞 |
| 源从 A→B→A 的受控发布 | hash 恢复，不自动复活旧审核 | 使用 03 受控 `binding_generation` |
| 从可信备份恢复原字节损坏 | 不等同于重新发布 | 保留恢复事件，重新核对当前绑定/撤销/授权 |

03 增强版把字节锁、语义绑定代际、当前准入守卫分开；06 应接入其受控版本，而不是按 mtime 或扫描次数自行制造 generation。没有受控绑定历史时只能证明本次看到的字节是否一致，不能声称检测过未观察到的 A→B→A。[^P03E]

#### 4.2.13 在途运行、缓存与并发读

运行已开始后，固定输入保持不变，不切换到新插件版本；来源漂移由核心决定取消或阻断后续转换，并记录实际顺序。06 不自行终止进程。旧运行的真实历史不能被后来撤销改写成“从未启动”。

缓存键至少包括锁摘要、核心解释 refs、路径/Schema/模板政策、目标能力/环境要求及当前相关守卫版本。内容解析缓存与当前授权缓存分离；不得缓存一个无限期 `valid=true`。进度事件、无关 profile 或无关插件变更不应该无条件清空全部锁缓存。

并发读者先 pin 固定引用；发布者只生成新版本。引用创建、卸载与 GC 的关系必须由同一受控索引/事务协调，不能依赖“暂时没看到活跃进程”。

#### 4.2.14 卸载、pin 与垃圾回收

卸载先停止新选择，不立即删证据。至少检查：当前启用项、待审草稿、已审核但未启动合同、排队工作流、运行中任务、未完成候选复核、历史保留期、导出/备份任务和故障恢复引用。

建议 mark–sweep 流程：从受信 root refs 计算可达对象 → 标记候选 → 经过宽限期和二次引用核对 → 在受控 GC 租约/事务下删除。新 pin 与删除必须互斥或使用版本守卫；删除失败保留状态并可重试。临时 build lease 保护尚未登记但将被引用的封存对象。

06 首期可以只提供“引用查询与卸载阻塞”，不必一次实现整个 GC。没有完整引用根集合之前，默认保留对象，而不是为了磁盘整洁删除未知历史证据。

### 4.3 权限与检查边界

#### 4.3.1 权限公式：需求不参与授权并集

原文的有效权限为用户授权、项目策略、角色允许集合、合同授权的交集。插件声明仅提出“需要什么”。[^P06]

```text
EffectiveAuthority = User ∩ Project ∩ Role ∩ Contract
RequiredAuthority = 当前完整插件组合的需求集合
Gaps = RequiredAuthority − EffectiveAuthority
可满足需求 ⇔ Gaps 为空，且当前撤销/保护路径/期限等守卫通过
```

授权集合不是简单的字符串集合。真实比较对象至少包含 action、资源/路径作用域、网络目标或工具身份、限制和有效时段；不能因为两边都有 `fs.write` 就判定覆盖。拒绝优先规则、既有保护路径、证据只读等限制继续独立生效。

#### 4.3.2 作用域绑定与约束交集

manifest 中 `scope` 建议使用受信 scope registry 的 ID，而非任意绝对路径、glob 或 URL。核心将其绑定到本次 workspace、工具、外发端点等固定对象，再与现有授权比较。

| 场景 | 正确判断 |
|---|---|
| 用户允许读 src，插件要求写 src | 不满足 |
| 合同允许执行固定检查 A，插件要求任意 shell | 不满足 |
| 用户允许端点 X，插件声明 X 和 Y | Y 为具体缺口；不因 X 已允许而整体放行 |
| 四层都允许，但目标触及受保护证据 | 保护规则仍阻止，插件不能覆盖 |
| 只有两层授权有数据 | 缺失层不能视作全量允许；按既有政策拒绝/待核验 |
| 预算未知或缺少额度 | 07 决定准入；插件校验不授予费用 |

首版参考只实现四组精确 `(action,scope_id)` 原子的交集，用于证明“需求不会增加权限”；不实现真实路径包含关系、网络策略、凭据、预算或 OS 执行控制。

#### 4.3.3 缺口输出与授权更新

缺口报告应逐项给出：请求插件/步骤、action、受控 scope、缺少哪一层、现有安全引用和可行的缩小方式。不得自动安装依赖、启用网络、修改保护路径、让插件注册自己的审核或调用其他 profile。

主模型已有明确业务授权时按既有流程继续，不为每个插件字段重复索要同一授权；但新增权限要求不能因锁生成成功而自动获得。任何授权更新须产生受信记录并重新核验相关输入，不改旧 lock 文件写一个 `allowed:true`。

#### 4.3.4 检查模板到正式命令

原文要求检查模板先进入审核，正式合同锁定相应命令后才由核心 runner 执行；沿用 05 的 argv/shell 与平台变体，不另造通用 shell 字符串拼装。[^P05][^P06]

推荐四层对象：

| 层 | 对象与所有者 | 何时可执行 |
|---|---|---|
| 声明 | manifest 中 check ID、定义资源、所关联步骤；06 | 不可执行 |
| 原始检查模板 | 05 CommandSpec/CommandSet 的受控候选；插件资源 | 仅可做静态校验 |
| 固定检查集合 | 核心绑定 artifact/worktree/tool/resource 后的正式定义 | 合同/审核覆盖后仍需当前准入 |
| 最终调用计划 | 05 FinalLaunchPlan，含真实入口、cwd、环境和限额 | 03/07/05 handoff 通过后执行 |

常量 argv 必须保持参数边界。涉及资源/产物/工具位置时，使用核心按 schema 允许位置建立的类型化绑定，不在整个 JSON 上做字符串替换。绑定不得改变 command id、required、超时上限、预期退出码、平台集合或核心检查身份。

本版不向 05 原 Schema 暗加 `{{input...}}` 表达式。若实施需要 BindingSpec，应作为独立核心记录定义 target JSON Pointer、binding kind、fixed ResourceRef，并在完整 CommandSpec 校验前消解；未知位置/重复写入/未绑定槽位均拒绝。

#### 4.3.5 平台覆盖与 required 语义

对全部声明平台静态验证每项检查的有效载体。必需/可选、cwd、timeout、expected exit、输出断言这些共同语义不能藏在某个平台分支中覆盖。缺 windows 实现不等于 optional 可自动跳过；不支持的平台组合在锁定前失败。

本版参考检查故意仅接受一个**合成 argv-only 子集**：id、required、cwd、timeout、expected_exit_code、by_platform。它不是 05 全量 CommandSpec 实现，也不涵盖 shell、断言、入口链和最终环境锁；真实接线必须注入已锁定的 05 校验器。[^P05E]

#### 4.3.6 插件检查与核心门禁

插件可以增加有命名空间的业务检查，不能直接声明 PASS、替换 G0–G6、降低核心检查为 optional、修改固定候选、重写 stderr 或原始事件。输出文本中的“PASS/测试通过”只是报告数据，既不授予权限，也不能代替独立检查证据。[^P04][^P06]

manifest/检查定义中的未授权 `verdict`、`skip_core_gates`、`replace_check` 或 `write_evidence` 字段在结构/语义层拒绝。业务报告里出现文字 PASS 可被原样留证，但核心不将其反序列化为内部 verdict 对象。

检查执行必须针对核心指定的固定候选/产物，不接受插件临时把路径切回主工作区或更早的产物。候选身份、检查定义引用、运行结果和验收归属仍由既有门禁绑定。

#### 4.3.7 输出契约与权限隔离

插件输出至少分成：角色报告、业务结构化数据、产物引用、核心执行证据。前两者来自模型/插件，是待验证数据；产物引用必须经核心核验文件存在、范围、完整字节和大小；进程/检查/门禁事实只能来自受信执行层。

输出按锁定 output schema 校验，并检查超限、截断、重复 JSON 键、未知引用和路径范围。生成文件路径由核心分配或受控映射；插件不能把 `../../.agent/runs/...` 当合法 artifact。输出 schema 通过不证明结论真实，也不直接满足核心验收。

#### 4.3.8 运行授权竞态与模块交接

插件锁和源快照有效，仍需在实际 handoff 前核对当前授权、环境与 controller generation。数据库准入和 OS 进程创建不是天然原子；已经外发的请求不会因审核撤销自动撤回。出现启动状态未知时沿用 03/05 的 `START_UNKNOWN` 协议，不由 06 自动重跑检查。[^P03E][^P05E]

插件验证发现漂移只输出稳定拒绝和引用，不偷偷修改进程参数、重绑 tool、换 shell 或重试模型。07 决定取消/重试，预算继续归属原 `request_id`。

#### 4.3.9 不可信内容与日志

错误和审阅差异仅展示安全资源 ID、相对位置、size/hash 及变更类别；业务正文、密钥、完整环境和绝对用户目录不出现在普通日志。需查看敏感 diff 时走具备相应权限的受控渠道。

描述、注释、模板、schema title/description 都是数据，不能充当验证器指令。禁止通过 `pickle`、不安全 YAML、自定义对象构造、动态 module import 或模板扩展来加载声明。首期只使用严格 JSON 与字节/文本资源。

#### 4.3.10 实现职责的最终检查

正式代码审阅需追问：纯解析是否存在进程/网络副作用？校验器是否有 HTTP/file URI 兜底？检查模板是否改变核心门禁？锁外文件是否能被模板/CLI 隐式加载？路径核验与读取是否固定对象？当前授权是否独立核验？是否出现 `locked/approved/PASS` 从插件数据流入权威状态？

任何一项没有可复查证据，就登记为未完成或阻塞项，不用“插件受信”一句话替代实施边界。

### 6.3 无执行副作用的评审模式

建议评审入口输出：enabled、依赖图、每插件来源与版本、资源清单、策略版本、平台覆盖、能力/权限缺口、锁候选摘要及与旧锁的安全差异。它不启动 CLI，也不修改当前启用配置或正式锁。

评审预览 hash 只有在最终写出的字节完全相同时才可沿用；合同编译或资源补齐后内容改变必须生成新 hash。预览不应展示 `ready_to_run:true` 之类可能与真实准入混淆的字段。

### 6.4 差异报告建议

差异按 `PLUGIN_ADDED/REMOVED`、`VERSION_CHANGED`、`RESOURCE_ADDED/REMOVED/BYTES_CHANGED`、`DEPENDENCY_CHANGED`、`CHECK_CHANGED`、`PERMISSION_REQUIREMENT_CHANGED`、`POLICY_CHANGED`、`SOURCE_BINDING_CHANGED` 分类。

安全报告至少包含旧/新 ResourceRef、影响插件、受影响合同/审核引用和修复动作。相同字节但定位变化单列；权限需求增加不能藏在“配置格式化”中；无关插件变化也要明确“未进入本对象闭包”。

## 8. 兼容与恢复

### 8.1 v1/v2 分支

原文保留：v1 按原 Schema/Pi 路径执行，不追补历史插件锁，不宣称已有 v2 插件保证。v2 需要相应审核与锁，不能删字段或改 schema 标签绕回 v1。[^P06]

启用 v2 插件前明确版本来源、迁移状态和目标合同。回退软件入口不自动迁移新合同，也不删除已生成的新审核/新锁。禁用插件只影响新选择，不能破坏仍需复查的旧引用。

### 8.2 操作人员恢复流程

| 步骤 | 操作 | 成功判据 | 失败升级 |
|---|---|---|---|
| R1 限制影响 | 暂停受影响 scope 的新派遣，不删除运行证据 | 新动作被阻断，在途状态可见 | 无法安全限定时由监督层扩大隔离 |
| R2 固定现场 | 保存安全诊断、head/generation、operation、锁引用、缺失/漂移清单 | 能重建故障时间线，未泄露正文/密钥 | 证据存储不可用则不继续发布 |
| R3 确认提交 | 按 operation 查询账本，区分孤儿/已提交/未知 | 确定是否存在权威登记 | 无法判断时维持 UNKNOWN_COMMIT，不盲重发 |
| R4 核对对象 | 用固定引用校验 lock 及全部文件 | 内容完整且来自允许存储 | 精确字节无法恢复则重新生成并重审 |
| R5 核对守卫 | 检查相关 binding、信任撤销、授权、环境和恢复高水位 | 当前状态可信且允许相应动作 | 旧备份/外部授权不可达则继续阻塞 |
| R6 选择修复 | 精确恢复原 bytes，或生成明确的新版本；两者分别留证 | 不回填旧合同/审核，不覆盖历史 | 不允许忽略 hash 或减少 checks |
| R7 同步投影 | 从已提交不可变 lock 更新当前 JSON 投影 | 与 head 引用完整字节一致 | 标明投影滞后，不伪称新锁未提交 |
| R8 验证恢复 | 执行固定的静态核验，再按准入恢复新派遣 | prepare/run 一致，原故障场景有记录 | 反复失败转为明确阻塞及维护任务 |

这些是操作步骤，不是假装已有可调用的 `plugin repair` CLI。正式实施时应把每步映射到真实只读查询/维护命令、权限与日志位置，避免操作人员临时拼接删除命令。

### 8.3 典型恢复决策

**模板单字节被改**：保留旧 lock/审核，报告资源差异；选择恢复可信原字节或生成新插件版本/新锁/新审核。恢复字节并不免除当前授权/绑定检查。

**当前投影损坏但不可变锁完整**：优先依据账本 head 与固定引用恢复投影，不扫描“最近修改”的 JSON 猜当前锁。

**未知启动**：先按 05 核对进程与运行身份，插件模块不再执行检查命令。确认重跑需要新运行及当前授权，预算仍归原 request。

**卸载后旧运行无法复核**：从受信内容库/备份恢复固定资源，不能安装“相同版本最新内容”冒充历史字节。没有原字节时明确证据缺失，不反向推定旧验收成立。

### 8.4 明确禁止的恢复捷径

不提供 `--ignore-hash`、自动去掉依赖、把 required 改为 false、清空 core_refs、自动信任目录、重算历史 hash、从模型报告重建批准、删除旧锁以消除冲突或改 schema 逃回 v1。原文“恢复仍不削弱门禁”的要求保持不变。

def read_regular(root: Path, relative: str) -> bytes:
    """Pinned descriptor read; NOT a multi-file atomic snapshot or OS sandbox."""
    relative_path(relative)
    if os.name != 'posix' or not hasattr(os, 'O_NOFOLLOW') or os.open not in os.supports_dir_fd:
        fail('E_NATIVE_BACKEND_REQUIRED')
    flags = os.O_RDONLY | os.O_NOFOLLOW | getattr(os, 'O_CLOEXEC', 0)
    fds = []
    try:
        fds.append(os.open(root, flags | os.O_DIRECTORY))
        parts = relative.split('/')
        for component in parts[:-1]:
            fds.append(os.open(component, flags | os.O_DIRECTORY, dir_fd=fds[-1]))
        fd = os.open(parts[-1], flags | os.O_NONBLOCK, dir_fd=fds[-1]); fds.append(fd)
        before = os.fstat(fd)
        if not stat.S_ISREG(before.st_mode): fail('E_PLUGIN_FILE_TYPE')
        if before.st_nlink != 1: fail('E_PLUGIN_HARDLINK')
        if before.st_size > MAX_FILE: fail('E_PLUGIN_FILE_LIMIT')
        parts_out, size = [], 0
        while True:
            b = os.read(fd, min(65536, MAX_FILE + 1 - size))
            if not b: break
            parts_out.append(b); size += len(b)
            if size > MAX_FILE: fail('E_PLUGIN_FILE_LIMIT')
        after = os.fstat(fd)
        stamp = lambda s: (s.st_dev, s.st_ino, s.st_size, s.st_mtime_ns, s.st_ctime_ns, s.st_nlink)
        if stamp(before) != stamp(after) or size != after.st_size: fail('E_PLUGIN_READ_DRIFT')
        return b''.join(parts_out)
    except Reject: raise
    except OSError: fail('E_PLUGIN_FILE_READ')
    finally:
        for fd in reversed(fds): os.close(fd)

def verify(raw: bytes, expected_sha: str, repo: Path, catalog: dict, enabled: list[dict], core_refs: list[dict]) -> Resolved:
    if sha(raw) != expected_sha: fail('E_LOCK_HASH')
    value = strict_json(raw); schema_check(value,'lock.schema.json','E_LOCK_SCHEMA')
    result = resolve(repo,catalog,enabled,core_refs)
    if canonical(result.lock) != raw: fail('E_LOCK_DRIFT')
    return result

def preflight(result: Resolved, platform: str, role_capabilities: dict[str,set[str]],
              authorities: list[set[tuple[str,str]]]) -> dict:
    if platform not in {'linux','macos','windows'}: fail('E_PLUGIN_PLATFORM')
    if len(authorities) != 4: fail('E_PERMISSION_INPUT')
    effective = set.intersection(*(set(x) for x in authorities))
    missing, required = set(), set()
    for pid,m in result.manifests.items():
        if platform not in m['platforms']: fail('E_PLUGIN_PLATFORM',chain=(pid,))
        for role in m['roles']:
            if role not in role_capabilities: fail('E_PLUGIN_ROLE',chain=(pid,))
        for cap in m['requires_capabilities']:
            if cap['id'] not in role_capabilities[cap['role']]: fail('E_PLUGIN_CAPABILITY',chain=(pid,))
        required |= {(p['action'],p['scope']) for p in m['permissions']}
    missing = required - effective
    return {'requirements_satisfied':not missing,'required':sorted(required),
            'effective':sorted(effective),'missing':sorted(missing),'evidence_kind':'synthetic'}
