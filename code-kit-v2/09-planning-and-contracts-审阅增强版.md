## 1. 目标与非目标

### 1.1 原文目标与完成定义

本模块将仓库调查、任务拆分和合同起草交给**可配置的独立 planner CLI**，主模型保留审核、设计决定与异常裁决。先规划任务图，等上游真实基线就绪后再细化具体合同；经主模型审核和调度器受控发布，形成 Markdown/JSON 双格式正式合同。规划与执行可以使用不同 CLI/profile/model，交接不能依赖共享聊天历史。[^P09]

完成 09 不等于“CLI 输出了一份看起来像合同的 Markdown”。建议完成定义为：在 01–08 已实现并验证的基础上，系统能够把获准的规划请求转换为可追溯的调查、任务图和草稿；对固定双格式字节完成有效审核；以可恢复、可核对的方式登记并发布；任意消费入口均不能把半份合同、伪审核、未来基线或过期输入当成可派遣对象。

### 1.2 非目标与现有边界

**原文保留**：planner 不自我审核、不直接派遣、不自动集成、不修改产品代码；不能因为需要保存草稿就放宽普通 Pi 执行器对管理目录的限制。规划失败不通过切换模型、放宽权限、读取凭据文件或复用旧审核来继续。[^P09]

本版进一步明确：09 不重写 03 的审核有效性、05 的进程监督、06 的插件锁、07 的预算与领取，也不把 08 的插件声明当成已经执行的验收结果。本文不选定第二个真实 CLI，不定义未知厂商参数，不替代 G0–G6 或人工规划路径。

### 1.3 审阅结论与优先补强项

原文已经定义了正确的流程边界；实施缺口主要集中在“对象怎样区分、谁提供可信字段、什么时刻可见、失败后如何恢复”。下表是本次设计分析，不表示这些问题已经在实际代码中发生。

| 缺口 | 潜在错误 | 本版处理 |
|---|---|---|
| PlanningBundle 只有字段组，没有字段级约束 | 模型用 `approved`、输出路径或伪造版本越过入口 | 4.2 的严格 Schema、字段拥有者及上下文绑定 |
| 调查基线与未来合同基线未分成不同对象 | 为未来任务填入猜测 SHA，或把图审核当执行许可 | 4.1 的双层基线和模板状态 |
| 来源“存在”与事实“得到支持”未分层 | 引用真实文件却声称已经跑过测试 | 4.2 的来源、坐标、语义支持和复审层次 |
| 草稿版本、图版本与正式版本容易混用 | 修复覆盖旧草稿；旧版本晚到替换新合同 | 2.2、4.4 的分配、冻结和 CAS |
| 两个合同文件缺少共同可见性协议 | 两次 rename 中断后半份合同被旧入口扫描并派遣 | 4.4 的登记账本与完整性门禁 |
| 正式路径缺少 request 层级 | 不同 request 中相同 task_id 发生文件名碰撞 | 4.4 的仓库级名称登记 |
| “有限格式修复”没有判别标准 | 借修 JSON 更改架构、权限、基线、检查 | 4.5 的修复类别、差异复核和机械停止 |
| 发布状态与审核当前有效性未分开 | 幂等返回历史发布后，被误认为旧审核恢复有效 | 4.4/4.5 的事实、投影、有效性分层 |

### 1.4 不可弱化的不变量

| 编号 | 不变量 |
|---|---|
| I01 | `request_id` 是预算根；图修订、草稿修复、CLI 切换和合同新版本均不重置它。 |
| I02 | planner 只输出建议数据；核心分配持久身份、目录、版本和发布位置。 |
| I03 | 调查事实、假设、设计决定、主模型审核、实际执行和验收结果必须分开。 |
| I04 | 未来合同未绑定真实基线时不可发布；图通过不等于未来合同已批准。 |
| I05 | 可细化不依赖尚未生成的正式合同；启动规划本身仍需权限、能力和预算。 |
| I06 | setup/check/插件调用在草稿阶段只做静态检查，不因“验证草稿”而执行。 |
| I07 | 主模型审核的是具体 MD/JSON 字节及相关输入；审核后不重排、不换行、不回填字段。 |
| I08 | 文件存在、登记提交、双格式完整、审核有效和可派遣是不同事实。 |
| I09 | 发布只能追加新版本；历史草稿、审核、原始流、attempt 和旧合同不得就地修补。 |
| I10 | 发布重试不能重复发布；未知规划启动不能触发无条件第二次模型调用。 |
| I11 | 受控入口只证明流程路径；同账户无隔离环境中不声称 OS 级身份隔离。 |
| I12 | 结构有效、来源坐标有效、合成测试通过均不能替代业务语义审核与真实集成验收。 |

### 2.2 身份与版本：四条修订链不能混用

| 字段 | 分配者与作用域 | 规则 |
|---|---|---|
| `request_id` | 核心；一次用户目标 | 后续所有规划、执行、修复与费用沿用 |
| `task_id` | 图中的稳定任务身份；受核心校验 | 任务拆分/合并需显式映射，不按标题猜测延续 |
| `graph_version` | 核心；request 内 | 改边、端口、任务边界、预计范围或要求，形成新图版本 |
| `draft_revision` | 核心；request 内单调递增 | `.agent/drafts/<request-id>/vN/` 的 N；不同任务细化也分配不同修订 |
| `plan_version` | 核心；正式任务合同版本 | 先保留版本槽，再冻结待审字节；不能由 planner 选择或覆盖 |
| `run_id` | 核心；一次实际角色调用 | 新调用使用新值；vendor session 不替代它 |
| `planning_operation_id` | 03/07/05 协调层 | 一次可能启动模型的副作用操作；重放不创建第二次调用 |
| `publication_id` | 核心；一次登记提交 | 不是 approval_id，不承载自身授权 |
| `publication_head_generation` | 发布账本；任务发布关系 | CAS 比较用；不以时间戳决定谁较新 |
| `binding_generation` | 03 的受控资源绑定 | 用于检测已受控发布的 A→B→A，不从文件 mtime 推导 |

**新增规则**：草稿可多次修订而尚未占用正式版本；一旦某个正式版本槽绑定待审候选，该候选不可变。主模型要求改字节时，生成新草稿和新候选，正式版本可以留有空号。空号不是错误，也不能通过回收版本号隐藏曾经审核或中断的候选。

生产系统必须另定废弃槽位记录与保留期；不能让 planner 一次响应保留无限正式版本。附录只演示版本不可覆盖与单调分配，不实现完整版本配额。

### 2.3 建议新增记录

| 记录 | 最小内容 | 能证明什么／不能证明什么 |
|---|---|---|
| `PlannerRequest` | 用途、上下文引用、预算来源、输出协议和约束 | 受控调用输入；不是执行合同 |
| `ContextManifest` | 实际提供的资源、片段、裁剪与来源映射 | planner 接触了哪些受控数据；不证明读过所有文件 |
| `PlanningBundle` | 事实、假设、问题、图、草稿、预算建议、停止条件 | 结构化规划建议；不是批准 |
| `BundleValidationReport` | 结构、来源、图和静态领域错误 | 哪些机械检查通过；不证明设计正确 |
| `ContractCandidate` | 两个已封存文件、目标路径、渲染器和输入引用 | 主模型应审核的确切发布候选 |

## 4. 接口和行为约束

### 4.1 两级规划

#### 4.1.1 第一层：任务图，不提前承诺未来合同

**原文保留**：第一次规划输出目标、任务 ID、依赖、预计范围、验收意图、风险、预算与未决问题。依赖上游实现的节点只保留合同草稿模板；主模型可以审核拆分思路，但不等于批准未来具体执行合同。[^P09]

建议区分两个基线字段：

| 字段 | 含义 | 允许状态 |
|---|---|---|
| `investigation_baseline_ref` | 本次调查实际依据的仓库输入 | 必须是核心提供且可核对的固定基线资源 |
| `contract_drafts[].baseline` | 某个未来合同将消费的执行基线 | `unbound` 或 `bound`；两种结构互斥 |

```json
{"state":"unbound","reason":"依赖上游任务接受及真实基线使用授权，当前仅保留模板"}
```

`unbound` 不包含 `base_sha`、候选 SHA 或“预计 commit”。调查在真实 B0 上完成，并不意味着所有未来节点都可以用 B0 执行。任务图中能够确定的约束应保存；未来 API 的具体符号、路径或返回行为尚未确定时，记录接口需求和待细化项，不把假设写成调查事实。

首期建议第一层只产生图与模板，完整待发布合同由第二层产生，即使是无上游根任务也按两步处理。这样可以减少一份响应同时承担图审核和合同审核的混淆；该规则是新增的简化方案，不是原文宣称的已有行为。

#### 4.1.2 第二层：三个判断分别计算

沿用 07 的定义：[^P07][^P07E]

```text
can_refine = necessary_upstream_accepted
             AND fixed_inputs_available
             AND real_baseline_exists
             AND baseline_use_authorized

can_start_planner = can_refine
                    AND planning_call_authorized
                    AND planner_profile_and_environment_verified
                    AND planning_budget_reserved
                    AND planning_inputs_locked
                    AND request_not_stopped

can_execute = can_refine
              AND formal_pair_registered_and_complete
              AND execution_review_current
              AND inputs_and_environment_match
              AND execution_permissions_and_budget_available
              AND no_unresolved_scheduling_conflict
```

无上游节点使用已确认的当前输入；它并非自动获准启动外部规划模型。`can_refine=true` 表示材料条件成立，不是长期许可，也不要求尚未产生的正式合同。启动 planner 的瞬间仍调用 03/07 当前守卫，不缓存一个 `true` 跨越基线变更或撤销。

本版不将“执行环境尚未齐备”反向变成禁止保存调查/模板的理由。可以得到结构有效但带缺口的草稿；缺失的精确执行环境、检查定义或插件锁使其无法进入正式审核/发布，而不是伪填空锁或虚构预检记录。

#### 4.1.3 状态判定矩阵

| 上游与基线 | 规划条件 | 正式合同 | 可以做什么 | 不能做什么 |
|---|---|---|---|---|
| 上游未接受 | 无论 planner 是否可用 | 无 | 保存任务图、模板及等待理由 | 对假想最终代码生成可发布合同 |
| 上游已接受，但只有未提交补丁、无提交创建/使用授权 | 可用 | 无 | 请求主模型处理真实基线来源 | 自动 commit、合并或替换 base_sha |
| 上游接受、真实提交可解析且获准使用 | 权限/预算缺失 | 无 | 标记可细化但不可启动规划 | 把可细化当成模型调用许可 |
| 同上 | 全部满足 | 无 | 启动合同细化、保存草稿 | 等待可执行形成自依赖 |
| 同上 | 已完成细化 | 审核缺失或发布不完整 | 展示缺口、恢复发布 | prepare/run |
| 全部满足且输入未漂移 | 当前执行资源与授权有效 | 完整且审核有效 | 交 07 判断执行领取 | 09 直接启动执行器 |

#### 4.1.4 基线核验输入与调查视图

基线记录建议包含 repository namespace、Git 存储对象格式、完整 commit OID、输入覆盖说明、上游 AcceptedResult 引用及基线使用授权来源。先校验 OID 字面格式，再按受信 argv 调用已有 Git 核验接口。Git 提供 `rev-parse --verify`、类型限定和 `--end-of-options`；但“能解析 commit”仍不证明它包含所需上游内容或已经获准使用。[^W06]

生产核验至少区分：对象不存在、对象不是 commit、仓库不匹配、必要内容不在基线中、上游接受已撤销、缺少使用权限。浅克隆、缺失对象或稀疏检出不自动触发 fetch、安装 Git LFS 或子模块初始化；缺少必要字节就报告缺口。

调查应针对核心固定的仓库视图，记录该视图是否包含未提交差异、未跟踪输入、子模块、LFS 内容及稀疏范围。不能只记录 HEAD 而让 planner 实际阅读另一个漂移的工作区。

Git linked worktree 并非完全独立仓库，存在共享仓库元数据。因此“独立 worktree”不是保密、只读或身份隔离的证明；需要真实系统约束时由 05/既有安全层落实。[^W07]

#### 4.1.5 细化输入必须足以跨 CLI 交接

细化请求至少提供：原始需求和已决定的解释、锁定图与目标节点、真实基线及必要上游接受/产物、适用规则、可选插件与类型、现有能力缺口、已确认设计决定、目标平台、明确预算及停止条件。

不得使用“沿用上轮讨论”“你知道之前怎么做”“参考最新结果”等隐含引用。若上下文超限，核心生成 `ContextManifest`，明确实际提供与省略的内容、各片段来源和裁剪规则；缺失会影响合同正确性时停止细化，不凭摘要补出具体命令或代码行为。

#### 4.1.6 图变更与重新细化

改图涉及以下任一内容时生成新 `graph_version`：任务增删或拆并、依赖边、产物映射、验收责任、范围、共享接口和预算策略。细化过程中发现图不成立，planner 输出问题和变更建议，不直接更改已锁图后继续发布。

影响计算建议从发生变化的节点/端口向后求可达集合，再结合共享文件、接口和资源依赖补充受影响任务。该计算只产生待复审集合；不能自动撤销或接受业务设计。与当前合同无关的展示顺序、进度消息或另一 profile 不应触发全局失效，最终以 03 的相关依赖锁为准。

#### 4.1.7 完整时序示例

```text
需求 R → 在实际 B0 调查 → 图 G1：修复 A → 文档 B
    → 主模型审核 G1 的拆分与约束（没有批准 B 的未来合同）
    → A 在 B0 可细化 → 获准 planner 调用 → 草稿 D2
    → 冻结 A.v1 的 MD/JSON → 主模型审核 → 成对发布
    → 07 领取 A → 固定候选 K1 → 检查 K1 → 主模型接受
    → 仅有补丁、无候选提交权限：B 等待
    → 已按既有授权取得真实提交 B1，并获准作为 B 基线
    → B 可细化 → planner 重新调查 B1 → 生成 B.v1 草稿
    → 针对 B1 的新审核和发布 → 07 再判断 B 可执行
```

同一合同的“改动→固定候选→检查→verdict”仍是阶段顺序；不把检查阶段拆成等待本任务先 PASS 的跨任务边。规划阶段产出的调查若仍有效，可以引用，不为了凑阶段重复启动模型。[^P08]

### 4.2 PlanningBundle

#### 4.2.1 新规划协议与字段拥有者

原文要求新规划协议标识不得复用 `TASK:`。建议受控请求家族为 `record_type=planner-request`，用途显式为 `graph` 或 `refine`，经 04 已登记的输出通道返回 `planning-bundle`。这只是新协议提案，不是任何真实 CLI 已支持的参数或原始事件名。

| 字段／值 | 谁可以提供 | 核心必须做什么 |
|---|---|---|
| request/task/run 上下文 | 核心提供；planner 可回显关联值 | 与调用登记逐字段比较，不信任回显身份 |
| 草稿与正式版本、文件目录 | 核心分配 | planner 输出这类未声明字段即拒绝，不拼接任意路径 |
| 事实、假设、任务图、草稿内容 | planner 提议 | 校验来源和结构，交主模型复审 |
| 审核、授权、锁已生效、PASS | 03/07/既有门禁的可信记录 | planner 自声明不能进入权威状态 |
| CLI/model/用量/进程结束 | 04/05 的运行证据 | 不从 bundle 自述反填缺失元数据 |
| 预算建议 | planner 提议 | 不高于请求上限；实际预留和扣账仍由 07 执行 |

建议 `PlannerRequest` 的关键字段如下；它由核心生成，不是模型可自行补写的配置：

| 字段 | 类型／约束 | 必要行为 |
|---|---|---|
| `record_type/schema_version` | 固定家族及显式版本 | 未知版本拒绝，不能回退 TASK 协议 |
| `request_id/run_id/operation_id` | 01 身份 | 新调用与同操作重放分开 |
| `mode/target_task_id` | graph 时目标为空；refine 时目标存在 | 不允许一次细化顺便改其他任务合同 |
| `requirements_ref/context_manifest_ref` | 固定 ResourceRef | 提供实际原始需求与上下文范围 |
| `graph_ref/baseline_ref` | graph_ref 按用途可为空；调查基线必需 | 不从模型自行给出的 SHA 找基线 |
| `planner_config_ref/environment_ref` | 02/04/05 封存资源 | 新 profile 或环境变化按前序规则处理 |
| `catalog_ref/rules_refs/decision_refs` | 受信固定输入 | 不开启隐式资源发现 |
| `output_contract_ref` | 输出 Schema、协议及上限 | 不接受另一份模型自带 Schema |
| `planning_budget_ref/authorization_refs` | 07/既有授权 | 引用不自动构成准入；启动时再核验 |
| `repair_policy_ref/stop_policy_ref` | 固定策略 | 不让模型更改最大重试次数 |

#### 4.2.2 结果提取与严格入口

建议处理顺序：

```text
05 原始流与 TransportSummary
 → 04 固定 parser 解释身份、工具、终止与用量
 → 确定唯一规划结果的来源事件／产物
 → 有界读取与 UTF-8/JSON 校验
 → PlanningBundle Schema
 → 调用上下文／允许资源校验
 → 来源坐标／图／类型／草稿检查
 → 保存不可变草稿和 ValidationReport
 → NEEDS_PLAN_REVIEW 或明确阻塞
```

不能从任意 stdout 文本中用宽松正则“找第一个 `{...}`”；不能扫描聊天内容选择最像合同的一块；不能从模型声称的输出文件路径读取未分配文件。

同一已识别结果事件的重放可以由来源身份去重；**两个不同事件即使内容相同，也不是当然的一次结果**。首期建议多份最终结果一律返回歧义，除非锁定协议明确规定其关系。内容不同更不能按“最后一份”覆盖。协议结束、采集完整和实际模型证据不足时，保存可解析草稿片段作为未完成证据，不升级为有效正式草稿。

Python 默认 JSON 解码会接受重复键并保留最后一个值，也接受部分非有限数；只在输出使用 `allow_nan=False` 不足以保护输入。本版要求输入端拒绝重复键、非有限数、无效 Unicode 和尾随第二文档。[^W01]

建议首版限额：bundle 原始字节 1 MiB、嵌套深度 64、任务 128 个、单任务阶段 64 个、事实 256 条、单事实证据 32 段、单文本字段最多 16,384 个 Unicode 字符（不是 UTF-8 字节；整体仍受 1 MiB 限制）。**这些是待压测的设计初值，不是已测性能或厂商限制。** 图/事实超过限额时分批细化或缩小范围，不静默截掉尾部后继续审核。

09 的附录 JSON profile 不含实数字段；整数拒绝 `1.0`/`1e2`，费用需要时以 07 的十进制字符串记录。此限制只适用于本版记录，不能倒推修改 01 的所有历史 JSON。

#### 4.2.3 顶层字段合同

所有对象默认拒绝未知字段；02 的 `_...` 说明字段例外不扩展到 bundle、合同和审核。JSON Schema 需明确 `required` 和封闭对象规则，不能把 `properties` 当成必填声明。[^P02][^W04]

| 字段 | 必填与取值 | 语义 |
|---|---|---|
| `record_type/schema_version` | 必填，planning-bundle / 1（建议） | 独立新记录家族 |
| `request_id/planner_request_ref` | 必填 | 同调用登记一致；请求引用锁定完整请求 |
| `mode` | graph / refine | 决定以下字段和草稿约束 |
| `graph_ref` | graph 为 null；refine 为固定引用 | 细化不能暗改已锁任务图 |
| `target_task_id` | graph 为 null；refine 为存在的任务 ID | 首期一次细化一个任务 |
| `investigation_baseline_ref` | 固定引用 | 本轮实际调查的输入，不是未来全部合同的基线 |
| `requirement_refs` | 非空、无重复 | 与请求提供的需求集合核对 |
| `facts` | 可为空 | 没查到事实时用空数组和问题，不生成假事实 |
| `assumptions/questions` | 显式数组，可为空 | 未决与已决不能靠删除数组项混淆 |
| `risks` | 显式数组，可为空 | 关联受影响任务、影响估计、缓解建议及可选决定来源；不是风险接受证明 |
| `task_graph` | 非空任务集合与显式边 | 包含任务级验收、预计范围和阶段 |
| `contract_drafts` | graph 可有模板；refine 一份目标草稿 | complete 不等于 approved |
| `budget_proposal` | 非负约束与显式机械上限 | 仅建议，不是记账事实 |
| `stop_conditions` | 非空的已登记停止类别 | 不能覆盖父请求更严格的停止规则 |

`null` 只用于 Schema 明确允许的未绑定字段；缺失必填字段不能解释为 null。空字符串、`latest`、`TBD-SHA`、估计模型 ID 和伪造完整十六进制 SHA 都不是“有效占位”。结构上形似哈希的字符串仍需真实资源/基线解析器确认。

#### 4.2.4 事实来源：四层验证，不能混成一个 confidence

| 层 | 检查内容 | 结论边界 |
|---|---|---|
| S1 结构 | 引用、坐标、类型与长度 | 只是字段合法 |
| S2 资源完整性 | 来源在允许集合内、完整文件哈希正确 | 确认是哪个固定对象 |
| S3 证据定位 | 半开字节区间、UTF-8 边界、片段摘要匹配 | 确认引用了来源的哪段字节 |
| S4 语义支持 | 引用内容是否支持具体事实、是否超出调查范围 | 需要规则与主模型复审；不能靠哈希证明 |

建议证据坐标使用 `[start_byte, end_byte)`，相对于**被引用的那份实际字节资源**。若来源已脱敏或提取，坐标指向脱敏/提取资源，另记录原来源链，不能仍指向变化前的偏移。展示行号为派生便利字段，不能替代字节定位。

同一事实可引用多个片段；多个片段各自核验。引用仓库源码说明“代码里有测试函数”，不能声明“测试已经通过”；runtime observation 必须关联可信执行证据。模型输出里写了 `source_kind=runtime` 也不能把普通文件升级为运行事实。

“未发现某符号”只能在明确扫描范围、搜索方法、输入版本和工具结果内成立。只阅读一个文件不能证明整个仓库不存在某实现。源码中的注释、README 说明和运行报告可能互相矛盾，应保留矛盾和各自来源，交主模型处理，不自动选择最符合草稿的一条。

附录实现 S1–S3 的部分有界验证，并返回 `semantic_support_verified=false`；这是能力边界，不是要求正式系统永远不做 S4。

#### 4.2.5 假设、问题、决定与需求覆盖

建议假设具有 `unconfirmed/confirmed/rejected` 状态；问题具有 `open/resolved` 状态。标记 confirmed、rejected 或 resolved 时必须引用主模型/业务层已登记的决定，而不是由 planner 用一句“默认采用”完成关闭。正式系统还要验证决定的主体、范围、当前状态与相关性；仅有引用 shape 不够。

问题声明 `blocks=[graph_review/refine/publish]` 及受影响 task_ids；空 task_ids 表示当前范围全部受影响。是否阻断须来自已锁规则或主模型判断，不能让 planner 在得知问题严重后自行把 blocks 改空。

需求覆盖建议构造：

```text
原始需求引用 → 稳定需求条目 ID → 任务节点 → 行为条款 → 验收意图／检查来源
```

结构检查可以发现遗漏 ID、引用不存在或一项要求完全没有任务承担；它不能证明任务或检查真正覆盖需求语义。延期/排除需求必须有主模型决定引用，不能直接删除该需求。原型只实现严格“全部需求 ID 至少被一个任务引用”，不实现延期豁免。

风险条目建议包含 `id/description/task_ids/impact/mitigation/decision_ref`。`impact=low/medium/high/unknown` 是 planner 的定性建议，不是已测概率或主模型接受结论；`unknown` 不能归入低风险。空数组只表示没有列出风险，不证明任务没有风险。附录校验风险 ID、任务端点和决定引用种类，不自动证明缓解有效；重大未决风险应同时登记阻断问题，由主模型决定是否继续。

#### 4.2.6 任务图、阶段和类型检查

任务节点至少包含稳定 ID、目标、依赖、需求 ID、预计写范围、验收意图、阶段组合与预算建议。引用的插件步骤、输出和输入类型应来自 06/08 固定目录，不能仅凭显示名称匹配。

校验顺序建议为：任务 ID 唯一→依赖端点存在→任务图无环→需求覆盖→各任务阶段图无环→输入映射只引用合法前驱→候选冻结/检查顺序→固定输出类型与输入要求→平台覆盖和能力缺口→预计冲突与范围诊断。

任务 DAG 和阶段 DAG 分开报错；`depends_on` 不由数组顺序推定。Schema 兼容必须按 07 的受限类型规则证明，不能用“一条样例可以通过验证”代替通用兼容性证明。附录仅验证显式依赖和 freeze/check/verdict 的部分祖先关系，**不实现生产端口映射、插件编译或完整候选身份关联**。

#### 4.2.7 草稿完整度、字段来源与静态命令验证

草稿 `completeness=template/complete` 只是文档完整度。完整草稿还可能因为未决设计、执行环境缺口或授权不足而无法发布；不使用名为 `ready=true` 的混合字段。

| 草稿字段 | 来源 | 缺失／冲突处理 |
|---|---|---|
| baseline | 07 已确认并获准使用的真实输入 | 未绑定保留 template；complete 不允许伪 SHA |
| scope_paths | 任务图、既有权限、主模型决定 | 细化超出图的预计范围时产生变更建议，不静默扩张 |
| executor_profile_ref | 02 中已定义配置 | 模型不能写新 provider/model 覆盖 |
| environment_ref | 04/05 的实际执行环境记录 | 可保存草稿缺口，不能伪填环境通过 |
| plugin_lock_ref | 06 当前选定资源锁 | 必需锁未存在则阻塞，不写 `locked:true` |
| checks_ref | 05/08 的固定检查定义 | 只做静态检查；不从 README 拿命令直接执行 |
| narrative | 明确目标、非目标、行为和验收说明 | 与机器字段同源；非目标不能藏入不展示字段 |

正式合同编译器需要复用现有 `validate_plan`；命令字段要验证 argv 与 shell 互斥、平台覆盖、cwd、超时、断言和权限。命令“能解析”不等于“已经安全执行过”，命令“不要求网络”也不证明其运行不会隐式联网。

#### 4.2.8 共有字段同源生成，叙述条款也要锁

建议管线：`ValidatedDraft → ContractIR → 固定 Renderer → MD + JSON`。ContractIR 为受信编译器接受的中间表示，字段默认值、插件展开和规范化必须发生在冻结前。

所有影响执行的字段都从同一个 IR 生成；Markdown 不是独立可手工修改的第二份合同。行为说明、验收意图和非目标也进入审核输入，不能只锁机器命令而让人读的合同另有相反约定。

Markdown 需要防止模型字符串插入伪造的标题、HTML、隐藏内容或结束代码围栏。可以采用固定 AST 渲染器和受限富文本；附录仅用动态长度 literal fence 演示原文作为数据展示，不宣称完成完整的生产 Markdown 安全渲染。

审阅前先运行确定性重渲染比对和双格式一致性检查。审阅后不再通过渲染器输出“更好看的版本”；直接发布已经被审核的字节。原始 Markdown 的 SHA-256 以完整字节为准，不能在发布时转换为 CRLF 或再做 Unicode 归一化。Git 属性可能改变检出文本的行尾，因此正式资源存储与工作区展示必须明确分工。[^P01][^W08]

#### 4.2.9 冻结依赖与避免哈希环

建议依赖顺序如下：

```text
原始需求／基线／规则／配置／环境／插件及检查资源
                ↓
       ContextManifest / PlannerRequest
                ↓
        原始运行证据 → PlanningBundle
                ↓
        ContractIR → MD / JSON 文件
                ↓
     ContractCandidate（同时引用两文件及目标路径）
                ↓
        03 ApprovalRecord / InputLockReceipt
                ↓
          PublicationReceipt / 调度索引
```

候选描述符不能包含自身摘要；合同也不能回填 approval_id 或 publication_id。运行证据中的结果引用与事后索引要避免反向指向包含该结果摘要的前置请求。完整闭包由 03 的受信资源提取器及 06/09 类型规则共同构造，不能直接相信 planner 提供的精简 `input_refs`。

#### 4.2.10 草稿目录与保存行为

核心先为 request 分配全新 `draft_revision`，再在受控 staging 写入 bundle、校验报告、上下文来源及渲染候选；目录 `.agent/drafts/<request-id>/vN/` 只接受核心分配的标识。

写入失败保留已产生的原始证据与失败阶段。`DRAFT_READY` 要求需要的草稿对象已经完整封存；仅协议响应中出现完整 JSON 不足以进入该状态。失败修订和未完成文件不得成为“最新有效草稿”。

正式系统需追加草稿登记事务与当前修订 CAS，防止多个 planner 结果同时成为同一修订。附录没有实现完整草稿注册服务：它只为合成待审候选写入固定草稿资源，并在 SQLite 中登记候选。

### 4.3 规划权限与命令边界

#### 4.3.1 规划请求不是低风险免审路径

**原文保留**：planner 使用独立会话和仓库视图，默认调查而不修改产品代码；代码外发与费用在规划调用中同样存在，必须事先具有覆盖该调用的授权。本系列设计文档不构成外部规划模型调用授权。[^P09]

有效权限沿用 06 的交集：既有用户授权 ∩ 项目策略 ∩ planner 角色允许集合 ∩ 本次规划请求范围。profile 选择、插件声明或模型建议不能扩大其中任一项。

| 动作 | 默认处理 | 必要条件 |
|---|---|---|
| 读取明确的仓库文件/资源 | 按允许集合提供 | 实际读取范围、敏感信息与外发用途在授权内 |
| 读取环境配置/凭据 | 不向 planner 暴露凭据值 | 只提供受控引用和能力缺口，不传整个 HOME/环境 |
| 本地搜索/结构调查 | 仅已审工具和限定范围 | 有可靠隔离与能力证据；工具名本身不证明只读 |
| 写产品代码 | 禁止 | 另走正式执行合同，不在 planner 会话临时提权 |
| 写 `.agent/drafts/`、`.agent/plans/`、`.agent/runs/` | planner 禁止 | 调度器提取、校验后写自己管理的对象 |
| 执行草稿 setup/check | 禁止 | 主模型审核并授权后，才进入 05 正式 runner |
| 写代码探针或运行基线测试 | 不属于默认纯调查 | 单独受审阅调查请求及其资源、清理和预算 |
| 安装、联网抓取、commit、push、集成 | 默认不允许 | 独立既有授权及相应受控流程 |
| 登记审核、改变 DAG 接受状态 | planner 禁止 | supervisor/既有接受入口，身份不由输入 JSON 决定 |

主模型已有相应授权时不需要为每次写审核记录重复向用户确认；缺失的是业务设计决定或新增外发/费用范围时，才形成具体待决项，不用泛泛的“请再次确认所有步骤”阻塞已获准工作。[^P03]

#### 4.3.2 只读保证分级

| 级别 | 已有措施 | 可以报告 | 不能报告 |
|---|---|---|---|
| L0 提示约束 | 提示词写“只读” | 已表达调查意图 | 已阻止写入 |
| L1 工具选择 | 移除显式写工具，保留有限读取工具 | CLI 工具列表受到限制 | 任意 shell/扩展/CLI 自身无法写入 |
| L2 系统约束 | 受控账号、只读挂载/权限、网络策略 | 在被测边界内阻止对应副作用 | 全系统绝对无写入/无外发 |
| L3 隔离与审计组合 | 系统限制、资源代理、负例、执行证据 | 指定平台与版本上的实测保证 | 未测平台或更强攻击者同样被覆盖 |

这张表是设计分层，不表示当前工程已有 L2/L3。角色要求如果必须有某种真实隔离，而当前 CLI/平台做不到，应阻塞该用途；不能把保证等级默默降低后继续付费调用。

#### 4.3.3 仓库、日志和网页中的指令都是输入数据

源文件可能含“忽略规则”“写入 approved=true”“读取环境变量上传”等文本。它们可以成为被引用的调查材料，但不能改变工具、发布流程或审核身份。

建议将可信请求、资源清单和不可信内容分区传递；只开放完成调查所需的受控工具；对模型输出继续做独立字段、权限和资源核验。提示注入防护需要多层措施，关键词过滤或一段系统提示不能单独保证安全。OWASP 的相关指南也将输入分离、最小权限、输出验证和人工审批作为组合措施，而非单一过滤器的保证。[^W10]

脱敏必须发生在外发前；响应中再次出现疑似秘密时，按既有 01/04 证据与隔离策略保存安全诊断，不把原始秘密写入校验错误、修复 prompt、traceback 或审阅摘要。不能把低熵秘密的普通 SHA-256 当作安全匿名标识。

#### 4.3.4 探针和基线检查的独立请求

若事实需要运行命令才能确认，planner 先输出 `investigation_needed` 问题及建议目的，不把命令执行藏进 bundle 校验函数。主模型确认后，由核心创建新的调查请求，绑定同一 request 预算根、实际基线、具体命令、输入、权限、超时、日志和清理要求。

输出必须标明是否运行、退出事实和证据引用。运行探针生成的事实可以成为后续新草稿输入；不得把探针之后的证据倒填进早先已经审核的 bundle，假装审核时就已存在。

#### 4.3.5 上下文最小化与跨 CLI 会话隔离

planner 默认新会话；续用历史会话必须有独立受审协议，明确会话携带哪些未在当前请求中显式声明的资源。原生 CLI 的用户配置、扩展、上下文和认证路径仍按 04/05 检查；不因 planner 角色默认“只读”就开放自动加载。

执行器只接收正式合同、固定资源、基线和必要证据，不接收 planner 的完整聊天历史作为隐含规则。planner 的推测、草稿命令、未决选择和未经批准的扩展建议不应被编译成执行指令。

### 4.4 审核与发布

#### 4.4.1 三种审核对象与动作范围

**原文保留**：主模型重点审核需求覆盖、事实真实性、设计取舍、范围、测试辨别力、依赖、权限和预算；经受控 supervisor 入口写入 03 审核记录。planner 的 `approved:true`、伪造角色和旧审核引用均不能发布合同。[^P09]

| 对象 | 主模型审阅内容 | 不等于什么 |
|---|---|---|
| 任务图 | 拆分、依赖、风险、预计范围、预算分配和待决项 | 未来各节点的具体执行批准 |
| 调查请求 | 具体探针/基线检查、数据外发和副作用 | 任意命令长期许可 |
| 具体 ContractCandidate | 固定 MD/JSON、真实基线、完整输入锁和目标路径 | 自动派遣、验收、提交或集成 |

动作名由 03 的已登记动作表映射。可以采用“同一条具体合同审核覆盖发布及后续执行所需审阅动作”的方案，但必须显式记录；只覆盖 publish 的审核不能被 run 直接消费。发布与执行各自还要检查当前业务授权。

原型的 `approve_fixture()` 是测试替身，不实现主模型身份、动作范围、过期、条件、单一审核 head 或业务授权；生产代码不得使用这个接口。

#### 4.4.2 审阅包的最小内容

主模型应看到完整待发布 Markdown、完整机器合同、安全可读的关键字段差异、调查事实与出处、未决问题、固定基线、范围和保护路径诊断、检查设计、选择的 profile/环境/插件、预算与授权缺口。

摘要仅帮助定位，不能代替完整对象引用。若审阅包超出上下文容量，按任务/模块分批审阅并保存覆盖关系；必要条款未审阅时不能自动签发“完整合同通过”。

与旧版本比较时，应分别列出：需求变化、基线变化、范围变化、命令变化、权限/模型变化、插件或规则变化、仅说明性文字变化。主模型作出 CHANGES_REQUESTED 后，不能只更新 Markdown 解释而保持 JSON 中的旧行为。

#### 4.4.3 ContractCandidate 与源位置／发布位置

审核时正式路径尚未出现，不能让 `ResourceRef.path` 指向不存在的正式文件并声称已完整校验。建议候选描述符引用**已封存的草稿源文件**，并同时声明目标正式路径：

| 字段 | 内容 |
|---|---|
| `request_id/task_id/plan_version` | 核心分配并一致的身份 |
| `draft_revision` | 产出本候选的草稿修订 |
| `members[markdown]` | 源 MD 的 ResourceRef + `.agent/plans/<task>.vN.md` |
| `members[machine]` | 源 JSON 的 ResourceRef + `.agent/plans/<task>.vN.json` |
| `renderer_ref` | 固定渲染规则/实现的资源引用 |
| `input_refs` | 受信闭包，不含候选自身 |

候选必须恰好包含一个 markdown 成员和一个 machine 成员，角色与后缀一致，路径互不冲突，两份内容指向同一 request/task/version。审核绑定候选描述符及两份源文件，源位置→发布位置的映射也属于审核对象，不能发布时临时重定向。

正式 `PublicationReceipt` 再记录最终文件的定位及相同完整字节摘要，关联原 source_ref、candidate_ref 和 approval_ref。位置变更的可接受性来自这个已审核映射与当前受控定位检查，不是“哈希相同所以任意路径都可用”。

#### 4.4.4 仓库级任务名与版本预留

原文正式路径没有 request 层级，而 01/07 的任务身份在 request 中使用。因此，不同 request 的相同 task_id 可能竞争同一个正式文件名。**本版首期建议保留原路径，但增加仓库级 task_id 名称归属登记**：

```text
(repository_namespace, task_id) → owning_request_id
```

同一 request 延续原任务可追加版本；另一 request 申请相同名字时返回 `E_PLAN_NAMESPACE_COLLISION`。由核心和主模型在冻结前决定新任务名或以后版本的显式存储映射，不能静默覆盖，也不能只在文件名加后缀而让合同内部 ID 不变。

已存在但无可信登记的正式文件不得视为可覆盖空位。先按旧人工合同取证/迁移路径确认归属。以后改为包含 request 的路径需要独立存储协议与兼容迁移，本版不悄悄改变原路径。

版本预留需原子递增和幂等：同键同任务返回原槽位；同键不同任务冲突；失联或被放弃的槽位保留记录。较小版本晚到不得替换较大已发布版本；CAS 用实际发布 head generation，不用目录中最大的文件名推断状态。

#### 4.4.5 为什么两次 rename 不等于完整发布

一次成功的 `os.replace` 可以原子替换一个目录项，但它不把两个独立文件与数据库审核关联合成为一个跨资源事务；存在目标文件时还可能直接替换原内容。因此，不应把顺序写 MD、写 JSON、写 approved 标记称为“原子发布”。[^W02]

本版建议将发布保证拆为：

1. **内容不可变**：两份已审核文件及候选对象可按固定字节恢复，不覆盖不同内容。
2. **登记原子性**：一个权威事务提交双格式引用、审核关联、幂等映射、head 和发布事件。
3. **共同可消费性**：消费者只有在登记存在、两份文件完整匹配、当前审核与授权有效时才允许继续。

这是对所有受控消费入口的逻辑可见性保证，不承诺任意目录浏览器永远看不到 staging 或某个先出现的文件。若旧 `prepare` 仍能绕过登记直接按文件名消费，整个协议不成立，必须先修复该入口。

#### 4.4.6 建议发布步骤与线性化点

| 阶段 | 执行方 | 必须完成的检查／写入 | 对外含义 |
|---|---|---|---|
| P0 分配 | 核心 | 名称归属、版本槽、draft revision 和目标路径 | 仅保留身份 |
| P1 冻结 | 09/01 | 完整 MD/JSON、候选、渲染器与输入闭包；固定字节 | 待审对象可读取 |
| P2 审阅 | 主模型/03 | 审阅具体内容；登记审核、输入锁和动作范围 | 存在审阅事实 |
| P3 当前校验 | 03/09 | 审核有效、源字节未变、相关绑定与权限当前有效 | 某一观察点满足前置条件 |
| P4 登记提交 | 权威账本 | CAS、幂等、双格式引用、审核关联、发布序号和 outbox 同事务 | **发布登记的线性化点** |
| P5 文件投影 | 核心文件存储 | 原样发布两份字节；不覆盖不同内容；验证最终定位 | 可观察完整文件对 |
| P6 完整性确认 | 09/03 | 登记与两份文件一致；当前相关审核仍有效 | 合同发布完成的观察 |
| P7 执行消费 | 07/03/05 | prepare/run 重新做相关锁、权限、预算和准入 | 独立执行动作 |

参考选择 P4 先提交、P5 后投影：P4 中或其此前已可靠封存的受信对象存储保存可恢复的确切字节。这样文件丢失可以恢复，但在 P5 未完整时一律不能派遣。也可以设计“先发布不被消费的文件，再提交最终索引”，但必须完整定义另一套崩溃窗口，不得混用两种方案的证明。

本版允许 P4 已成功但 P5 失败；这会使当前版本处于不可派遣状态，不自动退回旧 head。可用性下降优于未经确认地执行旧版本。恢复成功也不能越过已经发生的审核撤销。

#### 4.4.7 账本约束与事务草案

下表是生产数据模型建议，不要求照搬附录的测试表名：

| 对象 | 关键唯一约束 | 主要用途 |
|---|---|---|
| 名称登记 | repo + task_id | 防止正式路径跨 request 冲突 |
| 版本保留 | repo + task_id + plan_version | 一槽一候选；放弃不复用 |
| 候选记录 | candidate_id／完整摘要；task + version 唯一 | 固定源字节与目标路径 |
| 发布记录 | publication_id；task + version 唯一 | 双格式与审核关联 |
| 当前发布 head | repo + task_id | generation 与当前 publication |
| 发布幂等键 | repo + request + 主体范围 + action + key | 防重放及跨主体泄露 |
| outbox | 事件稳定 ID 唯一 | 事务内登记，重复投影不重复派遣 |

以下是事务意图，不是可直接套入未知生产数据库的完整 SQL：

```sql
BEGIN IMMEDIATE;
-- 1. 在主体和 action 范围内查询幂等键；同键同指纹返回历史登记。
-- 2. 核对名称、版本槽、候选、03 当前审核与相关守卫高水位。
-- 3. 检查未有相同 task/version 发布；新版本大于当前正式版本。
-- 4. 将 publication、双成员引用、审核关联和必要 pin 写入。
UPDATE publication_heads
SET publication_id = :publication_id,
    generation = generation + 1
WHERE repository_namespace = :repo
  AND task_id = :task
  AND generation = :expected_generation;
-- 必须断言影响行数为 1；否则整个事务回滚。
-- 5. 写入幂等映射及 contract.registered outbox 事件。
COMMIT;
```

SQLite 同一时刻只允许一个写事务，`BEGIN IMMEDIATE` 可能返回 SQLITE_BUSY；它只是取得数据库写事务，不自动证明文件、外部授权服务或进程也在同一原子边界。[^W03]

若 03 与发布账本不在同一数据库，应采用受信版本化校验/消费协议并陈述撤销观察窗口；不能在事务外取得 `approved=true` 后声称实现了与撤销严格串行的发布。调用外部服务失败时 fail closed，保留可重试状态，不降低校验标准。

#### 4.4.8 持久性、对象文件与平台边界

目标存储实现须分别说明：进程异常终止、操作系统崩溃、断电、磁盘写满、目录同步失败、数据库恢复、文件权限和备份回退。SQLite 的原子提交依赖底层锁、同步与存储假设；应用外部文件不能因为“数据库事务成功”就自动获得相同保证。[^W05]

本地参考使用单 SQLite 文件、DELETE journal、FULL synchronous，以及同目录临时文件加不覆盖链接发布；当前仅在 Linux 容器测试。它不证明 Windows/macOS 原生恢复或掉电持久性。生产使用 05/06 的已审文件后端，不复制一段 pathlib 检查就声称消除了链接竞态。

不把可写账本放在未经验证的同步盘/网络共享目录后宣称多机安全。特别是 SQLite WAL 要求相关进程在同一主机，不能直接用网络文件系统实现该模式的跨主机共享。[^W09]

#### 4.4.9 发布幂等与返回行为

指纹至少包含：候选完整引用、两成员与目标映射、审核引用、正式版本槽、expected head generation 及影响发布的显式选项。排除服务器生成的 publication_id 和记录时间。幂等键是一次逻辑请求的稳定身份，不是合同标题。

| 场景 | 必须返回／处理 |
|---|---|
| 新键、合法请求 | 登记一次；返回 publication_id 和当前投影状态 |
| 同键、同指纹、已提交 | 返回原登记；不重发发布事件、不创建新版本 |
| 同键、不同指纹 | `E_IDEMPOTENCY_CONFLICT`，不覆盖 |
| 同键仍在处理中 | 有界等待或返回 IN_PROGRESS，不能并行创建第二次提交 |
| 提交成功但响应丢失 | 按原键查询；不能以超时推断未提交 |
| 原审核后来撤销或被替代 | 返回原登记事实，并明确当前不可消费 |
| 幂等记录未知或账本不可用 | 标明 UNKNOWN，不扫描文件猜成功、不生成新键盲重试 |
| 同候选用新键重复发布 | 返回明确已存在结果或冲突；不再次推进 head |

幂等历史返回不授予当前权限；主体查询权限也要重新检查。发布接口返回 `PUBLISHED` 时应附可见性观察时间或游标，不能作为未来任意时刻的 prepare/run 许可。

#### 4.4.10 消费者算法与固定字节消费

```text
输入：显式 task/version 或已登记 publication_id；当前调用主体与动作
1. 查权威登记，不以文件存在或“最新文件”作为起点。
2. 核验 task/request/version、审核关联、来源协议与当前发布关系。
3. 通过受控后端读取两份固定文件及候选描述符；拒绝缺失、重复角色或路径冲突。
4. 对本次实际读取的字节核验全部摘要及 MD/JSON 一致性。
5. 调用 03 公共校验：相关输入、绑定代际、当前审核、动作、授权及环境。
6. 由 07 完成预算、冲突与领取；03/05 按一次性准入再核验 handoff。
7. 消费刚才固定的同一组字节/对象版本，不重新跟随可变路径读取。
```

prepare 成功与 run 开始之间相关输入发生变化，run 仍须拒绝。单次有效性读取与后续文件替换/权限撤销之间存在竞态；应使用已固定资源和当前动作准入缩小窗口，但不宣称数据库能撤回已发送的网络数据或已启动进程。[^P03]

#### 4.4.11 发布后的精确失效

| 变化 | 默认处置 |
|---|---|
| 合同任一字节、需求、适用规则、检查、所选配置/插件变化 | 新输入、新候选和新审核；旧运行证据保留 |
| 基线或必要上游接受/产物变化 | 重新确认可细化，必要时重新调查与起草 |
| 执行环境变更 | 新预检；按 03 的环境锁要求决定重新审核，不仅看语义哈希 |
| 相关资源绑定 A→B→A | 使用可信 binding_generation；不能仅因哈希恢复自动复活审核 |
| 精确备份恢复相同原字节 | 维护流程登记；重新核对审核、绑定和当前授权，不等于新批准 |
| 无关任务进度、非所选 profile、简报读取游标 | 不应造成无关合同失效 |
| 控制器重启 | 旧在途操作按 controller generation 隔离；不自动重写全部已发布合同 |
| head 已指向新版本但投影不完整 | 当前任务保持阻塞；不隐式回退旧版 |

### 4.5 状态、修订与消耗

#### 4.5.1 保留规划状态，增加正交事实

原文状态链保持：`REQUESTED → PLANNING → DRAFT_READY → NEEDS_PLAN_REVIEW → APPROVED`。APPROVED 只表示相应审核有效，实际派遣仍要求完整发布和 prepare/run 门禁；不得把这些状态写进历史执行 attempt。[^P09]

建议展示时使用多个状态域，而不是让一个 APPROVED 字段承担全部含义：

| 状态域 | 建议字段／值 | 解释 |
|---|---|---|
| 规划阶段 | 原五个状态 | 当前草稿流程位置 |
| 阻塞原因 | BASELINE_WAIT、DECISION_REQUIRED、INFRA_BLOCKED、BUDGET_STOP、PROTOCOL_INCOMPLETE | 不擦除已有有效调查 |
| 调用事实 | NOT_STARTED、STARTED、START_UNKNOWN、EXITED | 来自 04/05/07，不由 bundle 自述 |
| 发布工作流 | RESERVED、CANDIDATE_SEALED、REVIEW_REGISTERED、REGISTERED、PAIR_COMPLETE | 描述物料和提交事实 |
| 当前有效性 | CURRENT、SUPERSEDED、REVOKED、STALE、INCOMPLETE、UNKNOWN | 随当前守卫变化的派生判断 |
| 执行状态 | 原 attempt/verdict 语义 | 与规划流程分开 |

新草稿修订开始时，旧修订保留其历史状态。被撤销的历史审核仍是当时的登记事实，但当前 APPROVED 投影必须失效；不能改旧记录的 decision，也不能继续把状态缓存当许可。

#### 4.5.2 建议转移与守卫

| 当前情形 | 输入／条件 | 后续处理 |
|---|---|---|
| REQUESTED | 07 就绪、权限、预算及输入锁满足 | 登记一次规划操作，再进入 PLANNING |
| PLANNING | 唯一完整结果、结构与上下文检查通过、草稿封存 | DRAFT_READY |
| PLANNING | 进程/结果未知 | 留在可解释的中断投影，标记 START_UNKNOWN/PROTOCOL_INCOMPLETE |
| DRAFT_READY | 审阅对象完整且必要字段已固定 | NEEDS_PLAN_REVIEW |
| NEEDS_PLAN_REVIEW | 主模型要求改动 | 新草稿修订，保留旧版本与理由 |
| NEEDS_PLAN_REVIEW | 有效具体审核登记 | 当前修订可显示 APPROVED |
| APPROVED | 原样登记及两成员完整 | 显示发布完成；由 07 独立判定执行就绪 |
| 任意阶段 | 停止、权限撤销或预算耗尽 | 禁止新增模型调用；允许已有证据归档和获准恢复 |

#### 4.5.3 格式修复与设计修订必须分开

| 类别 | 示例 | 允许处理 |
|---|---|---|
| 外层传输/抽取错误 | 截断、无终止、多份矛盾结果 | 先保留证据、确认实际运行；不从片段拼正式结果 |
| 纯结构错误 | 缺必填字段、错误枚举、重复任务 ID | 在允许次数/额度内发起新修复调用；完整重验 |
| 来源错误 | 引用缺失、字节范围错误、事实缺证据 | 补足真实材料或明确未知；不能伪造引用来满足 Schema |
| 设计矛盾 | 新架构、接口冲突、删除需求、扩大范围 | 主模型决定后生成新图或新草稿 |
| 运行环境错误 | CLI/凭据/平台能力缺失 | 报告基础设施缺口；不换模型或读秘密绕过 |
| 实现失败 | 验收不通过、候选错误 | 主模型判定返工还是合同修订，09 不自行归因 |

“缺字段修复”也可能改变语义。建议修复请求锁定原始需求、基线、图、模型、权限、插件与检查来源，返回字段差异报告；涉及这些关键值的变更转为设计修订。对先前无法解析的输出，无法证明其语义未变，应把新响应视为全新未审草稿，而不是宣称完成了无损修复。

不要把格式修复解释为服务器自动补默认模型、凭据、命令、正式版本或未来 SHA。模型自带的修复次数、`retryable=true` 和建议延长时限都不授权新调用。

#### 4.5.4 机械停止、循环检测与计量

建议 `max_repair_calls` 是允许的**新增修复模型调用数**，初始调用不计入该字段，但计入总 `max_calls`。要求 `0 ≤ max_repair_calls < max_calls`；实际可用次数取本次策略、规划子预算及 request 全局余量中的最严格上限。

例如，规划子预算允许 3 次调用、最多 1 次结构修复：初次响应失败后最多新增 1 次修复，不能因为子预算还剩 1 次就自动启动“换提示再试”。后续合同细化若另行获准，仍从同一 request 总额计量。

重复错误可用 `(输入上下文摘要, 错误家族, 安全字段位置, 关键语义差异摘要)` 辅助识别。相同失败再次出现可提前停止，避免直到额度耗尽；错误指纹仅用于控制策略，不替代保留原始证据。

所有 planner、格式修复、合同细化、另起的调查模型调用都进入 07 账本。取消、超时和失败也可能已经产生费用；没有费用字段就标记 unknown，不把它视为免费。当前主会话不可观测用量不能伪造为零，更不能据此计算“节省百分比”。[^P07]

预算检查应发生在实际 handoff 前，并使用 07 的原子预留。09 原型只检查预算建议没有超出给定上限，**没有实现真实预留、对账、token 计量或费用硬上限**。

#### 4.5.5 启动未知与迟到结果

07 已领取或 03 已准入，但无法确认 05 是否启动目标进程时，按 `START_UNKNOWN` 恢复；不能为了得到新草稿而盲目重发模型调用。

迟到结果必须仍关联原 run、request、操作和输入锁。如果其图/基线已被替代，可以保存为历史调查材料，标记当前不可发布；是否复用其中事实由主模型和固定来源校验决定，不能直接覆盖新草稿 head。

#### 4.5.6 跨层停止与恢复

request 已停止后，禁止新增规划、修复、执行或自动续会话；可以完成原始流排空、证据封存、费用对账、身份核对和已授权清理。恢复不是清空停止原因，而是追加由谁、依据什么决定恢复，以及新的预算/授权/输入检查。

主模型决定重新规划时，保留原 task/graph 的关系映射，不改 request_id 规避历史消耗。新任务名若确实代表新业务目标，也必须由业务层明确登记，而非由规划器在超预算后自行重命名。

#### 4.5.7 事件与诊断

09 建议输出 `planning.requested`、`planning.result_recorded`、`planning.validation_failed`、`draft.sealed`、`contract.candidate_sealed`、`contract.registered`、`contract.projection_checked`、`planning.stopped` 等已登记事件。事件包含稳定本地身份、来源引用、原因与必要安全字段，不包含明文凭据或整个模型上下文。

项目事件由 10 建立自己的游标，不把跨 run 时间戳当严格顺序；同一 outbox 重放不重复启动阶段。09 发布事件也不能冒充 04 的模型事件、05 的进程事实或 07 的任务接受事件。

| 错误家族（建议注册） | 典型条件 | 恢复方向 |
|---|---|---|
| `E_PLANNER_CONTEXT` / `E_PLANNER_INCOMPLETE` | 上下文错配、身份/终止/采集不足 | 核对原运行与固定输入 |
| `E_BUNDLE_*` / `E_JSON_*` | 空、多份、重复键、超限、截断 | 保留原始流，有限修复或停止 |
| `E_EVIDENCE_*` | 来源未提供、范围不合法、摘要或证据类别不符 | 补足材料，不能造证据 |
| `E_GRAPH_*` / `E_REQUIREMENT_*` | 环、悬空边、遗漏或未授权改图 | 新图/决定与重新审核 |
| `E_DRAFT_*` / `E_UNRESOLVED_DESIGN` | 未绑定基线、缺关键输入、待决问题 | 等待或细化，不发布 |
| `E_PLAN_NAMESPACE_COLLISION` / `E_VERSION_*` | 路径命名冲突、旧版本覆盖 | 分配合法身份/新版本 |
| `E_PUBLICATION_*` / `E_HEAD_CAS` | 不完整、冲突、未知提交 | 查询原键、核验账本与原字节 |
| `E_REVIEW_*` / `E_GUARD_STALE` | 伪审核、相关输入或守卫已变 | 调用 03，不能本地补 approved |

具体错误码须与 01 注册表协调。`details` 只含安全位置和可操作原因，不能直接输出验证库带原始输入的 exception；`retryable` 仅说明故障可能暂时，不授予新调用权限。

### 8.3 操作人员九步恢复流程

**第 1 步：停止新增派遣。** 使用已经实现的受控暂停机制停止 planner、修复和 executor 新调用；记录操作者、request 和事件游标。尚无暂停入口时由既有运维流程隔离新派遣，不编造命令名。

**第 2 步：保存现场。** 保存账本一致备份、相关候选/合同/审核资源清单、原始流和错误。SQLite 等数据库采用其已验证备份方法；不能在活跃写入时只复制单个数据库文件就宣称得到完整备份。SQLite 的 Online Backup API 可用于活跃数据库的一致快照备份；数据库外的合同资源仍需配套快照与恢复验证。[^W12]

**第 3 步：确认外部进程。** 依据 run、operation、主机/启动信息和 05 身份证据判断是否启动、退出或未知。PID 单独不足；未知时不 kill 未确认对象，也不启动替代进程。

**第 4 步：查询权威登记。** 在正确 repo/request/主体范围内查询原幂等键及 publication_id，区分未提交、已提交、响应未知与当前 head。无登记文件不能反向导入为批准。

**第 5 步：核验对象链。** 从 candidate_ref 到两个 source_ref、最终目标路径、renderer、input_refs 和 approval_ref 做完整字节核验。所有引用必须能定位；不得用当前同名配置替代当时快照。

**第 6 步：恢复缺失文件。** 仅从可信封存对象/账本保存的原字节恢复缺失成员；目标已存在且不同内容时先隔离并登记故障，再按维护授权处理。恢复不能触发 renderer 再生成近似内容。

**第 7 步：核对当前审核与授权。** 通过 03 验证撤销、替代、输入变化、绑定代际、动作和环境；合同完整但审核失效时保持不可派遣。控制器交接应隔离旧操作，不把历史合同改成从未发布。

**第 8 步：对账调用与停止条件。** 由 07 对账预留、迟到费用、unknown 敞口与最大修复次数。恢复过程不是新预算根；不知道已花多少不能补零。

**第 9 步：只恢复允许的下一步。** 符合全部条件时恢复单个明确动作；图待细化、合同待审、发布待补齐与执行可派遣分别显示。留下恢复报告、成功判据和剩余阻塞项，不一次性把所有 request 状态改为成功。

### 8.4 检查 SQL 与成功判据

以下查询只适用于附录的合成账本，不是生产操作手册中的现有表名：

```sql
PRAGMA integrity_check;
PRAGMA foreign_key_check;

SELECT task, generation, publication FROM heads ORDER BY task;

SELECT p.id, p.task, p.version, p.candidate, p.review,
       p.epoch, p.controller
FROM publications AS p ORDER BY p.task, p.version;

SELECT k.request, k.idem_key, k.publication
FROM publication_keys AS k
LEFT JOIN publications AS p ON p.id = k.publication
WHERE p.id IS NULL;

SELECT p.id
FROM publications AS p
LEFT JOIN candidates AS c ON c.digest = p.candidate
LEFT JOIN fixture_reviews AS r ON r.id = p.review
WHERE c.digest IS NULL OR r.id IS NULL;
```

正常参考账本的 integrity_check 返回 `ok`，foreign_key_check 与两条孤儿查询应无行。SQLite 外键约束必须按连接启用，不能只在建表语句写 REFERENCES 就假定所有连接都会执行。[^W11]

但 SQL 通过不证明磁盘两份文件存在、哈希匹配、审核仍有效或权限充分；这些必须由资源校验与当前守卫补充。

恢复成功至少同时满足：账本一致；关联对象可读取；MD/JSON 字节一致；无未解决启动未知；当前操作的相关审核/授权有效；预算和停止条件明确；所有入口共享同一发布门禁。缺任何一项，只能报告“恢复了部分证据”，不能报告可派遣。

## 附录 A：结构 Schema 与领域校验边界

### A.1 使用范围与验证顺序

下面三份 Schema 都是本版交付的完整**结构定义**。`PlanningBundle` 是 09 新家族的设计建议；`synthetic-contract-ir` 与带 `synthetic: true` 的候选 Schema 用于离线原型，不是实际项目的可派遣合同格式。不能删除 synthetic 字段或更改 schema_version 来获得执行资格。

执行顺序为严格 JSON → 对应固定 Schema → 可信调用上下文绑定 → 来源字节校验 → 图/问题/风险/草稿领域规则 → 当前审核与业务授权。前五步通过只产生 `VALID_UNREVIEWED`。源代码示例中的 Schema 由固定文件名加载，所有 `$ref` 为本文件 `$defs` 内引用；不接收模型提供的 Schema URL，不开启网络解析。

将来需要跨文件 Schema 时，应通过已固定的本地注册资源组合，不给任意 `$ref` 提供通用网络或文件读取器。`jsonschema` 的引用行为可通过 `referencing.Registry` 显式配置；添加自定义检索函数属于额外信任边界，不是本版默认能力。[^W13]

| 校验对象 | Schema 能检查 | 还需领域/实际系统检查 |
|---|---|---|
| ResourceRef | 字段、ID、摘要形状、path 字符长度 | 注册 kind、真实存在、合法定位、字节摘要、来源与权限 |
| mode/基线 | 枚举、绑定结构、null 形状 | graph/refine 对应上下文；真实 commit 与使用授权 |
| 图/阶段 | 节点字段、数组大小、依赖形状 | 端点、无环、类型映射、候选身份、平台和资源冲突 |
| 事实 | 文本、证据坐标与摘要形状 | 固定来源、UTF-8 边界、完整及片段哈希、语义支持 |
| 假设/问题/风险 | 必填状态、任务列表、影响与决定引用形状 | 主模型决定真实有效、影响范围、风险接受与缓解效果 |
| 双格式候选 | 两个成员的字段形状 | 角色恰好各一、源/目标映射、同源内容、当前授权 |
| 版本/预算 | 整数取值范围 | 原子版本分配、实际总账、修复许可、停止与并发预留 |

`maxLength` 是字符上限，不是 UTF-8 字节上限；本版整体原始输入还受 1 MiB 限制。`uniqueItems` 比较整个条目，不能自动证明任务 ID 唯一或引用没有逻辑版本冲突，这些规则在领域层检查。

以下 Schema 没有 `format: date-time` 字段。将来新增时间必须指定 01 时间契约和明确的格式断言策略，不可仅写一个 format 就声称已经执行校验。

"""Extract explicit artifact blocks; never execute their contents."""
from __future__ import annotations
import re
import sys
from pathlib import Path

PATTERN = re.compile(r'^<!-- artifact-file: ([A-Za-z0-9][A-Za-z0-9_./-]*) -->\n(`{3,})[^\n]*\n(.*?)^\2\n', re.M | re.S)

def extract(source: Path, destination: Path) -> int:
    text = source.read_text(encoding='utf-8')
    entries = PATTERN.findall(text)
    if not entries:
        raise ValueError('No artifact blocks')
    if destination.exists():
        raise ValueError('Destination must not exist')
    seen = set()
    for name, _, _ in entries:
        parts = name.split('/')
        if name in seen or any(p in ('', '.', '..') for p in parts):
            raise ValueError('Invalid or duplicate artifact path')
        seen.add(name)
    destination.mkdir(parents=True)
    for name, _, body in entries:
        path = destination / name
        path.parent.mkdir(parents=True, exist_ok=True)
        with path.open('xb') as stream:
            stream.write(body.encode('utf-8'))
    return len(entries)

if __name__ == '__main__':
    if len(sys.argv) != 3:

"""Offline, synthetic reference for section 09; never launches a model or command.

The resource store is an allowlisted in-memory fixture, not a production resolver.
Git truth, business authorization, semantic fact support, and OS isolation are
explicitly outside this module. Passing these checks is NOT execution approval.
"""
from __future__ import annotations

import copy
import hashlib
import json
import re
from dataclasses import dataclass
from pathlib import Path
from typing import Any

from jsonschema import Draft202012Validator

ROOT = Path(__file__).parent
MAX_BYTES = 1_048_576
MAX_DEPTH = 64
SAFE_INT = 9_007_199_254_740_991
ID = re.compile(r"[a-z][a-z0-9-]{0,63}\Z")
RESERVED = re.compile(r"(?:con|prn|aux|nul|com[1-9]|lpt[1-9])(?:\..*)?\Z", re.I)


class ProtocolError(ValueError):
    """Only a stable code and safe location; never echo raw input or credentials."""
    def __init__(self, code: str, location: str = "") -> None:
        self.code, self.location = code, location
        super().__init__(code + (":" + location if location else ""))


def need(condition: bool, code: str, location: str = "") -> None:
    if not condition:
        raise ProtocolError(code, location)


def sha(data: bytes) -> str:
    return hashlib.sha256(data).hexdigest()


def scalar_tree(value: Any, depth: int = 0) -> None:
    need(depth <= MAX_DEPTH, "E_JSON_DEPTH")
    if value is None or type(value) is bool:
        return
    if type(value) is int:
        need(-SAFE_INT <= value <= SAFE_INT, "E_JSON_INTEGER")
    elif type(value) is str:
        need(not any(0xD800 <= ord(c) <= 0xDFFF for c in value), "E_JSON_UNICODE")
    elif type(value) is list:
        for item in value:
            scalar_tree(item, depth + 1)
    elif type(value) is dict:
        for key, item in value.items():
            need(type(key) is str, "E_JSON_KEY")
            scalar_tree(key, depth + 1)
            scalar_tree(item, depth + 1)
    else:
        # This 09 proposal has integers and decimal strings, but no float fields.
        raise ProtocolError("E_JSON_NUMBER_OR_TYPE")


def canonical(value: Any) -> bytes:
    scalar_tree(value)
    return (json.dumps(value, ensure_ascii=False, sort_keys=True,
                       separators=(",", ":"), allow_nan=False) + "\n").encode("utf-8")


def strict_json(data: bytes) -> dict[str, Any]:
    need(type(data) is bytes, "E_JSON_INPUT")
    need(0 < len(data) <= MAX_BYTES, "E_JSON_SIZE")
    need(not data.startswith(b"\xef\xbb\xbf"), "E_JSON_BOM")
    try:
        text = data.decode("utf-8")
    except UnicodeDecodeError as exc:
        raise ProtocolError("E_JSON_UTF8") from exc
    # Bound nesting before the stdlib decoder allocates a deeply nested tree.
    depth, quoted, escaped = 0, False, False
    for char in text:
        if quoted:
            if escaped:
                escaped = False
            elif char == "\\":
                escaped = True
            elif char == '"':
                quoted = False
        elif char == '"':
            quoted = True
        elif char in "[{":
            depth += 1
            need(depth <= MAX_DEPTH, "E_JSON_DEPTH")
        elif char in "]}":
            depth -= 1
    def pairs(items: list[tuple[str, Any]]) -> dict[str, Any]:
        out: dict[str, Any] = {}
        for key, value in items:
            need(key not in out, "E_JSON_DUPLICATE_KEY")
            out[key] = value
        return out
    def forbidden(_: str) -> Any:
        raise ProtocolError("E_JSON_NUMBER_OR_TYPE")
    try:
        value = json.loads(text, object_pairs_hook=pairs,
                           parse_float=forbidden, parse_constant=forbidden)
    except (json.JSONDecodeError, RecursionError, ValueError) as exc:
        if isinstance(exc, ProtocolError):
            raise
        raise ProtocolError("E_JSON_SYNTAX") from exc
    scalar_tree(value)
    need(type(value) is dict, "E_JSON_ROOT")
    return value


def relpath(value: str) -> str:
    need(type(value) is str and 0 < len(value) <= 512, "E_PATH")
    need(not value.startswith("/") and "\\" not in value, "E_PATH")
    need(not any(ord(c) < 32 or ord(c) == 127 or c in ':*?"<>|' for c in value), "E_PATH")
    parts = value.split("/")
    for part in parts:
        need(part not in ("", ".", "..") and not part.endswith((" ", ".")), "E_PATH")
        need(not RESERVED.fullmatch(part), "E_PATH")
    return value


def check_schema(value: dict[str, Any], filename: str) -> None:
    # Only bundled schemas; callers cannot supply a schema URL or file path.
    need(filename in {"planning.schema.json", "candidate.schema.json",
                      "contract-ir.fixture.schema.json"}, "E_SCHEMA_REGISTRY")
    scalar_tree(value)
    schema = json.loads((ROOT / filename).read_text(encoding="utf-8"))
    validator = Draft202012Validator(schema)
    error = next(iter(validator.iter_errors(value)), None)
    if error is not None:
        loc = "/" + "/".join(str(x) for x in error.absolute_path)
        raise ProtocolError("E_SCHEMA", loc)


def resource(kind: str, identity: str, path: str, data: bytes) -> dict[str, str]:
    return {"kind": kind, "id": identity, "path": relpath(path), "sha256": sha(data)}


def refkey(ref: dict[str, str]) -> tuple[str, str, str, str]:
    return ref["kind"], ref["id"], ref["sha256"], relpath(ref["path"])


def refs_in(value: Any) -> list[dict[str, str]]:
    found: list[dict[str, str]] = []
    if type(value) is dict:
        if set(value) == {"kind", "id", "sha256", "path"}:
            found.append(value)
        else:
            for child in value.values():
                found.extend(refs_in(child))
    elif type(value) is list:
        for child in value:
            found.extend(refs_in(child))
    return found


def sorted_refs(refs: list[dict[str, str]]) -> list[dict[str, str]]:
    unique = {refkey(ref): ref for ref in refs}
    logical: dict[tuple[str, str], str] = {}
    for kind, identity, digest, _ in unique:
        old = logical.setdefault((kind, identity), digest)
        need(old == digest, "E_RESOURCE_VERSION_CONFLICT")
    return [unique[key] for key in sorted(unique)]

def topo(nodes: list[dict[str, Any]]) -> list[str]:
    by_id = {node["id"]: node for node in nodes}
    need(len(by_id) == len(nodes), "E_GRAPH_DUPLICATE")
    for node in nodes:
        need(len(node["depends_on"]) == len(set(node["depends_on"])), "E_GRAPH_DUPLICATE_EDGE")
        need(all(dep in by_id for dep in node["depends_on"]), "E_GRAPH_DANGLING")
    pending = {key: set(value["depends_on"]) for key, value in by_id.items()}
    order: list[str] = []
    while pending:
        ready = sorted(key for key, deps in pending.items() if not deps)
        need(bool(ready), "E_GRAPH_CYCLE")
        # Arrays are not an execution ordering source; dependencies are.
        for key in ready:
            order.append(key)
            del pending[key]
        for deps in pending.values():
            deps.difference_update(ready)
    return order


def check_stage_graph(stages: list[dict[str, Any]]) -> None:

def literal_block(text: str, language: str = "text") -> str:
    # A model string cannot terminate its own fence and insert active Markdown.
    fence = "`" * max(3, 1 + max((len(m.group()) for m in re.finditer(r"`+", text)), default=0))
    return f"{fence}{language}\n{text}\n{fence}\n"

        sections.append(f"## {name}\n" + literal_block("\n".join(ir["narrative"][key])))
    sections.append("## 同源机器字段（完整）\n" + literal_block(machine.decode("utf-8").rstrip("\n"), "json"))
    return ("\n".join(sections)).encode("utf-8"), machine

        need(previous == record["payload"], "E_EVENT_REPLAY_CONFLICT")
    need(len(by_event) == 1, "E_BUNDLE_COUNT")

def write_store(destination: Path) -> dict[str, Any]:
    """No installation, external call, approval, formal publication or Git action."""
    if destination.exists():
        raise FileExistsError("Sample destination must not already exist")
    examples, stores = sample_materials()
    destination.mkdir(parents=True, exist_ok=False)
    entries = []
    for mode, store in stores.items():
        for key, data in sorted(store.items()):
            kind, identity, digest, relative = key
            if sha(data) != digest:
                raise ValueError("Synthetic resource digest mismatch")
            target = destination / mode / relative
            target.parent.mkdir(parents=True, exist_ok=True)
            if target.exists():
                if target.read_bytes() != data:
                    raise ValueError("Synthetic locator collision")
            else:
                with target.open("xb") as stream:
                    stream.write(data)
            entries.append({"store": mode, "ref": {"kind": kind, "id": identity,
                            "sha256": digest, "path": relative}, "bytes": len(data)})
    for name, value in examples.items():
        target = destination / "examples" / name
        target.parent.mkdir(parents=True, exist_ok=True)
        with target.open("xb") as stream:
            stream.write((json.dumps(value, ensure_ascii=False, indent=2, allow_nan=False) + "\n").encode())
    manifest = {"synthetic": True, "production_authorized": False, "resources": entries}
    (destination / "resource-index.json").write_bytes(canonical(manifest))
    (destination / "DO-NOT-IMPORT.txt").write_text(
        "Synthetic fixtures only. Do not import this .agent tree into a real project.\n", encoding="utf-8")
    return manifest
